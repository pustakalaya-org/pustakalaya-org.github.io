    Chapter 6: Programming Quantum Computers¶

    Quantum programs are hybrid: classical code builds, compiles and analyses circuits that run on a quantum processor or simulator. This chapter walks through the main toolkits — Qiskit 2.x and IBM's runtime, Cirq, PennyLane, CUDA-Q, Q# and Azure Quantum, Amazon Braket, pytket and Guppy — plus interchange formats, simulators, cloud pricing, your first working circuits, and the testing and engineering habits that make quantum code reliable. Code snippets use APIs current as of October 2026.

    6.1 The Hybrid Quantum-Classical Workflow¶

    Real quantum programs are mostly classical code. A normal computer prepares the problem, builds and compiles circuits, sends them to a quantum processor (QPU) for many repeated 'shots', and then analyses the results — often in a loop where a classical optimiser adjusts circuit parameters and tries again. Learning to program quantum computers means learning this whole pipeline, not just the gates.

    Think of it like…

    It is like a chef (the classical computer) who tastes a sauce, adjusts the seasoning and sends it back to a special oven (the QPU) that only it can operate — round after round until the dish is right.

    Real-world example

    Aisha, a data scientist at fictional GreenGrid Energy, estimates the ground-state energy of a toy two-qubit Hamiltonian. Her Python script builds a parameterised circuit, asks an Estimator for the energy, and lets SciPy's COBYLA optimiser change the angles. After a few dozen rounds the energy reaches −1.4142, matching the exact answer computed by diagonalising the 4 × 4 matrix.

    How it works¶

    1. Map: translate the business or science problem into qubits, circuits and observables (e.g. a Hamiltonian).
    2. Optimise: transpile circuits for the target hardware's native gates and connectivity.
    3. Execute: run batches of circuits on a simulator or QPU through primitives such as Sampler and Estimator.
    4. Post-process: apply error mitigation, compute statistics and feed the result to a classical optimiser or analysis step.
    5. Repeat the loop until the answer converges, logging job IDs and settings for reproducibility.

    Who uses it

    Quantum software engineers, application scientists in chemistry, finance and logistics, and HPC teams integrating QPUs with supercomputers all build hybrid workflows.

    Key takeaway

    IBM calls this pipeline 'Qiskit patterns': Map → Optimise → Execute → Post-process — a handy structure for interview answers and project write-ups.

    Going deeper

    • Each QPU execution returns samples, not amplitudes: estimating an expectation value to precision ε needs on the order of 1/ε² shots, so 1% precision costs about 10,000 shots per observable group.
    • Queueing and network latency can exceed QPU time by orders of magnitude; execution modes such as IBM sessions and batches, or Braket Hybrid Jobs, keep the classical loop close to the QPU and give priority access.
    • Primitives separate what you want (samples from Sampler, expectation values from Estimator) from how the provider gets it, letting vendors add error suppression and mitigation server- or client-side without changing your code.
    • IBM's 'quantum-centric supercomputing' vision and work such as sample-based quantum diagonalisation (SQD) run large classical post-processing on HPC nodes, using the QPU to propose important configurations.
    • HPC centres integrate QPUs with job schedulers such as Slurm and with GPU clusters; NVIDIA's NVQLink and CUDA-Q target low-latency coupling for workloads like real-time decoding.

    Common mistakes & misconceptions

    • Thinking the QPU runs your whole program: it executes only the circuit; loops, optimisers and data handling stay classical.
    • Ignoring shot noise: an optimiser chasing random fluctuations can wander; choose noise-robust optimisers such as SPSA or COBYLA and enough shots.
    • Submitting each iteration as a separate queued job on a busy device: use sessions, batching or hybrid-job services to avoid hours of waiting.

    Try it: A tiny variational loop: classical optimiser + quantum Estimator (pip install qiskit scipy)¶

    import numpy as np
from scipy.optimize import minimize
from qiskit.circuit.library import real_amplitudes
from qiskit.quantum_info import SparsePauliOp
from qiskit.primitives import StatevectorEstimator

H = SparsePauliOp(["ZZ", "XI", "IX"], coeffs=[1.0, 0.5, 0.5])  # toy Hamiltonian
ansatz = real_amplitudes(2, reps=2)
est = StatevectorEstimator()

def energy(x):                       # quantum side: estimate <H>
    return float(est.run([(ansatz, H, x)]).result()[0].data.evs)

res = minimize(energy, np.zeros(ansatz.num_parameters), method="COBYLA")
print("VQE energy:", round(res.fun, 4))                       # -1.4142
print("exact     :", round(min(np.linalg.eigvalsh(H.to_matrix())), 4))

    6.2 Qiskit SDK 2.x: Circuits, Transpiler and Primitives¶

    Qiskit is IBM's open-source Python toolkit and the most widely used quantum SDK. You build circuits with QuantumCircuit, analyse states and operators with quantum_info, compile ('transpile') circuits for real hardware, and run them through the Sampler and Estimator primitives. The 2.x series (2.0 in 2025; 2.5.2 in August 2026) moved performance-critical code to Rust and added a C API.

    Think of it like…

    Qiskit is like a full workshop for a new kind of furniture: a design bench (circuits), measuring tools (quantum_info), a machine that cuts designs to fit a specific room (transpiler), and a delivery service (primitives) to whichever house — simulator or QPU — you choose.

    Real-world example

    Tomás, a computer-science undergraduate, writes a Bell-state circuit, checks its expectation value ⟨ZZ⟩ = 2 for the observable ZZ + XX + ZI with StatevectorEstimator, then transpiles it for a simulated backend at optimisation level 1. The compiled circuit has depth 3 with one CX; Aer's sampler returns about half '00' and half '11'.

    How it works¶

    1. pip install qiskit (plus qiskit-aer for fast noisy simulation).
    2. Build a QuantumCircuit, or use the circuit library (QFT, real_amplitudes, etc.).
    3. Inspect it with quantum_info (Statevector, Operator, SparsePauliOp) and draw it.
    4. Transpile with generate_preset_pass_manager(optimization_level, backend) to get an ISA circuit.
    5. Run PUBs (circuit, observables, parameter values) through Sampler or Estimator and read results from DataBin fields.

    Who uses it

    Students, researchers and professional quantum developers worldwide; Qiskit skills appear in most quantum software job adverts and IBM's developer certification.

    Key takeaway

    Know the V2 primitive result shape: result[0].data.meas.get_counts() for Sampler (register 'meas' from measure_all) and result[0].data.evs for Estimator.

    Going deeper

    • Qiskit follows semantic versioning with a new minor release about every three months; 2.0 (March 2025) removed qiskit.pulse, the V1 primitives and BackendV1, and later 2.x releases stayed backwards-compatible within the series.
    • Qiskit 2.4 made gridsynth the default for synthesising RZ rotations into Clifford+T and allowed Python extensions built on the C API; 2.5 added a MultiStagePassManager and Clifford+T and Pauli-based-computation presets, with typical 2-3× faster transpilation on Benchpress circuits.
    • A PUB (primitive unified bloc) bundles one circuit with observables and parameter values; Estimator broadcasts arrays of parameters and observables, so one job can evaluate many points of a parameter sweep.
    • Transpilation runs stages init → layout → routing → translation → optimisation → scheduling; Sabre layout and routing insert SWAPs for limited connectivity, and optimisation_level 0-3 trades compile time for fewer gates.
    • ISA (instruction set architecture) circuits use only the backend's native gates and connectivity; IBM hardware rejects non-ISA circuits, so always transpile first and call observable.apply_layout(isa.layout) for Estimator jobs.

    Common mistakes & misconceptions

    • Following pre-2024 tutorials: execute(), Aer.get_backend(), BackendV1 and V1 primitives are gone in Qiskit 2.x; use primitives and pass managers.
    • Forgetting Qiskit's little-endian bit order: qubit 0 is the rightmost character in result bitstrings.
    • Sending untranspiled circuits or forgetting apply_layout on observables, which gives errors or silently wrong qubit mappings.

    Try it: Qiskit 2.x basics: local primitives and transpilation (pip install qiskit qiskit-aer)¶

    from qiskit import QuantumCircuit
from qiskit.primitives import StatevectorSampler, StatevectorEstimator
from qiskit.quantum_info import SparsePauliOp
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_aer import AerSimulator

bell = QuantumCircuit(2); bell.h(0); bell.cx(0, 1)

# Estimator: expectation values
obs = SparsePauliOp(["ZZ", "XX", "ZI"])
print(StatevectorEstimator().run([(bell, obs)]).result()[0].data.evs)   # 2.0

# Sampler: bitstrings
meas = bell.measure_all(inplace=False)
res = StatevectorSampler().run([meas], shots=1000).result()
print(res[0].data.meas.get_counts())                                  # ~{'00': 500, '11': 500}

# Transpile to a backend's instruction set (ISA)
pm = generate_preset_pass_manager(optimization_level=1, backend=AerSimulator())
isa = pm.run(meas)
print(isa.count_ops(), isa.depth())

    6.3 IBM Quantum Platform, Runtime Primitives and Qiskit Functions¶

    IBM Quantum Platform is IBM's cloud service for running Qiskit programs on real IBM QPUs. You authenticate with an API key, pick a backend, transpile, and submit jobs through Sampler and Estimator, which can apply error suppression and mitigation for you. In 2026 IBM renamed the service 'IBM Quantum Compute service' (formerly Qiskit Runtime) and moved its primitives to a new client-side design built on an 'Executor'.

    Think of it like…

    It is like a professional print shop: you upload a press-ready file (an ISA circuit), choose quality options (error mitigation), and the shop schedules it on its presses and sends back the prints with a bill measured in minutes of press time.

    Real-world example

    Chen, a researcher at fictional Lakeside University, uses her Open Plan account (10 free QPU minutes per 28 days). She saves her API key once, asks for the least-busy 100+ qubit device, transpiles a 20-qubit GHZ circuit and runs 4,000 shots with Sampler. The job uses a few seconds of QPU time, so she can run many experiments before her allowance runs out.

    How it works¶

    1. Create an IBM Cloud account and Quantum instance; copy the API key and instance CRN.
    2. Save credentials once with QiskitRuntimeService.save_account(...) — keep keys out of notebooks and Git.
    3. Choose a backend (service.least_busy(...)) and transpile circuits to ISA form for it.
    4. Pick a primitive and options (shots, resilience level, dynamical decoupling, twirling) and an execution mode (job, batch or session).
    5. Submit, record the job ID, and retrieve results and usage later from the dashboard or API.

    Who uses it

    Researchers, students and enterprise teams using IBM hardware; IBM Quantum Network members such as universities, banks and labs run most of their experiments this way.

    Key takeaway

    As of qiskit-ibm-runtime 0.50 (September 2026), import Sampler and Estimator from executor_sampler / executor_estimator; the old server-side SamplerV2/EstimatorV2 classes are deprecated but follow the same interface.

    Going deeper

    • qiskit-ibm-runtime 0.47 (May 2026) introduced the Executor primitive and QuantumProgram, built with the samplomatic package for circuit annotations and randomisation; the directed execution model is labelled beta, and IBM says new capabilities will arrive in Executor first.
    • Release 0.49 (August 2026) renamed Qiskit Runtime to IBM Quantum Compute service (QiskitRuntimeService is also available as IBMQuantumComputeService); 0.50 (September 2026) added client-side Sampler and Estimator that pre- and post-process locally and run through Executor.
    • Execution modes: job (single request), batch (many independent jobs scheduled together) and session (exclusive iterative access); sessions are not available on the free Open Plan.
    • Qiskit Functions are higher-level services from IBM and partners — e.g. Q-CTRL's Fire Opal, Kipu Quantum's Iskay optimiser, Qunova's HI-VQE chemistry — available to Premium, Flex and On-Prem plan users, some as free trials.
    • Qiskit addons are open-source research tools that run alongside the primitives: SQD (sample-based quantum diagonalisation), OBP (operator backpropagation), MPF (multi-product formulas), circuit cutting and AQC-Tensor.

    Common mistakes & misconceptions

    • Pasting your API key into a notebook you later share: save it with save_account or an environment variable and rotate it if exposed.
    • Copying older tutorials that use the retired 'ibm_quantum' channel or execute(): update to current QiskitRuntimeService and primitive imports.
    • Forgetting that mitigation multiplies QPU time: higher resilience levels or many twirls consume your minutes faster.

    Try it: Run a Bell circuit on IBM hardware (pip install qiskit "qiskit-ibm-runtime>=0.50"; uses QPU time)¶

    from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit_ibm_runtime import QiskitRuntimeService
from qiskit_ibm_runtime.executor_sampler import Sampler
# older clients (< 0.50): from qiskit_ibm_runtime import SamplerV2 as Sampler

# one-time setup, stores credentials locally:
# QiskitRuntimeService.save_account(token="<your API key>", instance="<your CRN>")
service = QiskitRuntimeService()
backend = service.least_busy(operational=True, simulator=False)

qc = QuantumCircuit(2); qc.h(0); qc.cx(0, 1); qc.measure_all()
isa = generate_preset_pass_manager(backend=backend, optimization_level=1).run(qc)

job = Sampler(mode=backend).run([isa], shots=1000)
print("job id:", job.job_id())
print(job.result()[0].data.meas.get_counts())

    6.4 Cirq and Google's Quantum Software¶

    Cirq is Google Quantum AI's open-source Python framework for writing and running quantum circuits, designed around the details of real hardware such as qubit grids and timing 'moments'. Around it sit fast simulators (qsim), the Stim error-correction simulator, OpenFermion for chemistry and Qualtran for fault-tolerant algorithm design. Google's own Willow processors are accessed by selected research partners rather than a public cloud.

    Think of it like…

    If Qiskit is a well-stocked general workshop, Cirq is a precision lab bench built by the team that designs the instruments — very close to how the hardware actually behaves.

    Real-world example

    Ingrid, a physics master's student, writes a Bell circuit in Cirq with two LineQubits, simulates 1,000 repetitions and gets about 500 each of 0 and 3 (binary 00 and 11) in the histogram. She then swaps to qsim to simulate a 30-qubit random circuit on her workstation and uses Stim for a surface-code study in her QEC course.

    How it works¶

    1. pip install cirq (or cirq-core plus vendor modules such as cirq-google or cirq-ionq).
    2. Create qubits (LineQubit, GridQubit) and build a Circuit from operations organised into Moments.
    3. Simulate with cirq.Simulator, or qsimcirq for larger circuits.
    4. Apply transformers to optimise or compile circuits for a target device's gate set.
    5. Run on hardware through a vendor service (e.g. IonQ, Azure Quantum) or Google's access programmes.

    Who uses it

    Google Quantum AI researchers and partners, QEC researchers (Stim, PyMatching), chemistry teams using OpenFermion, and developers targeting IonQ, AQT or Pasqal through Cirq modules.

    Key takeaway

    Cirq results come back as integer-keyed histograms per measurement key; know that measurement keys, not classical registers, organise Cirq results.

    Going deeper

    • Cirq organises circuits into Moments — sets of operations that happen at the same time on disjoint qubits — which makes timing and hardware scheduling explicit; cirq 1.7 was current on PyPI in October 2026.
    • qsim is a C++ state-vector simulator with a Cirq interface (qsimcirq); Google states it can simulate up to about 40 qubits on a 90-core Intel Xeon workstation, and it supports GPU acceleration via cuQuantum.
    • Stim, written by Craig Gidney, simulates stabiliser circuits extremely fast and generates detector error models; with PyMatching it is the standard open toolchain for surface-code research.
    • Google opened a Willow Early Access Program in 2026 for selected research teams, with proposals due 15 May 2026; Google does not offer general public cloud access to its processors.
    • Qualtran expresses fault-tolerant algorithms as composable 'bloqs' and counts logical resources such as T and Toffoli gates, while OpenFermion converts molecular problems into qubit Hamiltonians.

    Common mistakes & misconceptions

    • Expecting Cirq to give you Google hardware access: you still need a programme invitation or a third-party provider.
    • Mixing up Cirq's integer histograms with bitstring orders: measurement key order determines which qubit is the most significant bit.
    • Using Cirq's default simulator for large circuits: switch to qsim or a GPU backend above roughly 20-25 qubits.

    6.5 PennyLane and Differentiable Quantum Programming¶

    PennyLane, created by Xanadu, treats quantum circuits like functions you can differentiate, just as deep-learning libraries do with neural networks. You write a Python function, decorate it as a QNode attached to a device, and PennyLane computes gradients automatically — on simulators or real hardware via plugins. It is the most popular framework for quantum machine learning and variational algorithms.

    Think of it like…

    PennyLane is like adding an automatic slope gauge to a hiking map: wherever you stand on the landscape of circuit parameters, it tells you which way is downhill so an optimiser can walk to the valley.

    Real-world example

    Lucas, an ML engineer at fictional Orbit Analytics, defines a two-qubit QNode returning ⟨Z⟩ on the second qubit after RY(θ) and CNOT. PennyLane reports the value cos(0.3) ≈ 0.955 and gradient −sin(0.3) ≈ −0.296; sixty gradient-descent steps drive the value to −1.0 at θ = π. He then swaps the device string to a GPU simulator without changing the circuit code.

    How it works¶

    1. pip install pennylane (plus a plugin or lightning.gpu for other backends).
    2. Create a device: qml.device('default.qubit', wires=2) or a hardware plugin device.
    3. Write the circuit as a Python function and decorate it with @qml.qnode(dev).
    4. Return measurements such as qml.expval, qml.probs or qml.sample.
    5. Differentiate with qml.grad or a JAX/PyTorch interface and optimise; optionally compile with qml.qjit (Catalyst).

    Who uses it

    Quantum machine-learning researchers, variational-algorithm developers, chemistry teams and educators; PennyLane's demos and Codebook are common learning resources.

    Key takeaway

    Remember the parameter-shift rule: for rotation gates, the exact gradient equals half the difference of the circuit evaluated at θ + π/2 and θ − π/2 — it works on real hardware.

    Going deeper

    • PennyLane 0.45 was current in October 2026; its differentiation methods include backpropagation (fast on simulators), adjoint differentiation (memory-efficient for state-vector simulators) and parameter-shift (works on hardware, costing two circuit runs per parameter).
    • The Lightning simulators (lightning.qubit for CPUs, lightning.gpu via NVIDIA cuQuantum, lightning.kokkos for many architectures) are C++ back ends that speed up gradients for tens of qubits.
    • Catalyst compiles hybrid programs with qml.qjit using MLIR and LLVM, so classical control flow and quantum operations run as one compiled program rather than many Python calls.
    • Plugins connect PennyLane to Qiskit/IBM, Amazon Braket, Cirq, Quantinuum and other back ends; Braket Hybrid Jobs can run PennyLane's embedded simulators with no extra per-minute simulator charge.
    • PennyLane Datasets provide pre-computed molecular Hamiltonians and spin systems, and the Codebook offers structured interactive lessons used by many beginners.

    Common mistakes & misconceptions

    • Using parameter-shift on a simulator with thousands of parameters: backprop or adjoint differentiation is far faster there.
    • Importing NumPy instead of pennylane.numpy (with autograd) and wondering why gradients are zero or missing.
    • Assuming quantum ML beats classical ML by default: barren plateaus and dequantisation results mean benchmarks against strong classical baselines are essential.

    Try it: A differentiable QNode and gradient descent (pip install pennylane)¶

    import pennylane as qml
from pennylane import numpy as np

dev = qml.device("default.qubit", wires=2)

@qml.qnode(dev)
def circuit(theta):
    qml.RY(theta, wires=0)
    qml.CNOT(wires=[0, 1])
    return qml.expval(qml.PauliZ(1))          # = cos(theta)

theta = np.array(0.3, requires_grad=True)
print(circuit(theta), qml.grad(circuit)(theta))   # 0.955, -0.296

opt = qml.GradientDescentOptimizer(stepsize=0.4)
for _ in range(60):
    theta = opt.step(circuit, theta)
print("minimum:", round(float(circuit(theta)), 4))  # -1.0

    6.6 NVIDIA CUDA-Q and GPU-Accelerated Quantum Development¶

    CUDA-Q is NVIDIA's open-source platform for writing quantum 'kernels' in Python or C++ that run on GPU-accelerated simulators or real QPUs from several vendors. It is designed for hybrid workloads where GPUs and QPUs work side by side — simulation, optimisation and increasingly real-time error-correction decoding. NVIDIA also links QPUs and GPUs with low-latency hardware (NVQLink).

    Think of it like…

    CUDA-Q is like a universal power adapter plus a turbo generator: one plug fits many quantum devices, and when no device is attached, the GPU 'generator' simulates them very quickly.

    Real-world example

    Sanjay, an HPC engineer at fictional Polar Labs, writes a Bell kernel with @cudaq.kernel and samples it on his laptop CPU. On the lab's A100 node he adds cudaq.set_target('nvidia') and simulates a 32-qubit version in seconds, then switches the target string to a cloud QPU provider for a hardware run — the kernel code stays the same.

    How it works¶

    1. pip install cudaq (Linux and, since 0.14, macOS CPU support; GPU targets need NVIDIA GPUs).
    2. Write a kernel with @cudaq.kernel using qvector, gates and mz measurements.
    3. Choose a target with cudaq.set_target: qpp-cpu, nvidia (GPU state vector), tensornet, or a QPU provider.
    4. Call cudaq.sample for counts or cudaq.observe for expectation values of spin operators.
    5. Scale up with multi-GPU or multi-QPU targets, or add libraries such as CUDA-Q QEC and Solvers.

    Who uses it

    HPC centres, GPU-heavy research groups, quantum hardware companies integrating with NVIDIA systems, and developers needing very fast simulation for algorithm research.

    Key takeaway

    Remember that CUDA-Q kernels are compiled (via MLIR to QIR), not interpreted Python — so only the supported subset of Python works inside a kernel.

    Going deeper

    • CUDA-Q's compiler lowers kernels through MLIR dialects such as Quake to QIR and LLVM, so the same kernel can target simulators or hardware; cudaq 0.16 was the latest PyPI release in October 2026.
    • GPU targets build on NVIDIA's cuQuantum libraries: 'nvidia' uses cuStateVec for state vectors (single or multi-GPU), while 'tensornet' and 'tensornet-mps' use cuTensorNet for larger, less entangled circuits.
    • CUDA-Q 0.14 (GTC 2026) added macOS CPU support, a Pre-Trajectory Sampling with Batch Execution feature for noisy simulation, and a first release of CUDA-Q Realtime for low-latency FPGA-GPU data transfer over NVQLink.
    • CUDA-Q QEC provides decoders and QEC experiment tools that run on GPUs, and CUDA-Q Solvers packages algorithms such as VQE and ADAPT-VQE for chemistry workloads.
    • NVQLink, announced by NVIDIA in 2025, is an open architecture for connecting QPU control systems to GPU supercomputers with microsecond-scale latency, aimed at real-time decoding and calibration.

    Common mistakes & misconceptions

    • Writing arbitrary Python inside a kernel: only a supported subset compiles, so keep data processing outside the kernel.
    • Assuming GPUs remove exponential cost: a 40-qubit state vector still needs 16 TiB in double precision; GPUs only make the feasible range faster.
    • Choosing the state-vector target for wide, shallow circuits: tensor-network targets often handle 50-plus qubits when entanglement is limited.

    Try it: A CUDA-Q kernel (pip install cudaq; GPU optional)¶

    import cudaq

@cudaq.kernel
def bell():
    q = cudaq.qvector(2)
    h(q[0])
    x.ctrl(q[0], q[1])      # CNOT
    mz(q)

# cudaq.set_target("nvidia")   # uncomment on a machine with an NVIDIA GPU
print(cudaq.draw(bell))
print(cudaq.sample(bell, shots_count=1000))   # e.g. { 00:503 11:497 }

    6.7 Q#, the Microsoft QDK and Azure Quantum¶

    Going deeper

    • The modern QDK (1.0 released in early 2024) was rewritten in Rust for speed and runs in browsers via WebAssembly; the qdk Python package (1.33 in October 2026) now bundles Q#, OpenQASM compilation, Azure submission and framework adapters.

    6.10 OpenQASM 3, QIR and Interchange Formats¶

    Interchange formats are shared languages that let quantum programs move between tools and hardware. OpenQASM is a text format for circuits — version 3 adds classical logic, loops, timing and subroutines. QIR (Quantum Intermediate Representation) is a lower-level format based on LLVM, used by compilers for programs with complex classical control. Using standards keeps your work portable across vendors.

    Think of it like…

    OpenQASM is like a PDF of your circuit — readable and portable; QIR is like a compiled machine-independent bytecode — less readable, but ready for many different compilers to consume.

    Real-world example

    Kwame, a consultant at fictional Bridgeline Advisory, exports a client's Qiskit circuit with qasm3.dumps and sends the text file to a colleague using Amazon Braket, which accepts OpenQASM 3 directly. Another teammate compiles the same OpenQASM through Microsoft's QDK to QIR to submit on an Azure Quantum target. One circuit, three ecosystems, no manual rewriting.

    How it works¶

    1. Write or export a circuit in OpenQASM 3 (e.g. qiskit.qasm3.dumps).
    2. Validate it with a parser such as the openqasm3 reference package.
    3. Import it into another SDK or submit it directly to services that accept OpenQASM (Braket, Azure Quantum, IBM).
    4. For programs with rich classical control, compile to QIR with a tool such as the QDK or CUDA-Q.
    5. Keep the source format in version control alongside a binary snapshot (e.g. QPY) for exact reproducibility.

    Who uses it

    Compiler engineers, SDK maintainers, consultants moving workloads between vendors, and anyone archiving experiments in a vendor-neutral format.

    Key takeaway

    Rule of thumb: OpenQASM 3 for human-readable portable circuits; QIR for compiled programs with classical control; QPY for exact Qiskit round-trips.

    Going deeper

    • OpenQASM 2.0 (Cross et al., 2017) described static circuits; OpenQASM 3 (Cross et al., ACM Transactions on Quantum Computing, 2022) adds typed classical variables, if/while/for, subroutines, extern calls, timing with delay and box, and pulse-level calibration through OpenPulse.
    • OpenQASM is governed by a Technical Steering Committee with members from several companies; the openqasm3 Python package (1.0.1) provides the reference abstract syntax tree and parser.
    • QIR builds on LLVM IR, so standard compiler infrastructure can optimise classical parts; the QIR Alliance, hosted under the Linux Foundation's Joint Development Foundation, maintains the specification and profiles such as Base and Adaptive.
    • Qiskit's qasm3.dumps exports natively, while qasm3.loads relies on the separate qiskit-qasm3-import package; QPY is Qiskit's binary format that round-trips every circuit detail including parameters and layouts.
    • Newer intermediate representations target error-corrected, hybrid programs: Quantinuum's HUGR (from Guppy), MLIR-based dialects in CUDA-Q (Quake) and PennyLane Catalyst, all designed for loops and real-time control.

    Common mistakes & misconceptions

    • Assuming every OpenQASM 3 feature is supported everywhere: many back ends accept only a subset (often no while loops or extern calls).
    • Confusing OpenQASM 2 and 3 files: the header line and gate libraries differ, and some tools accept only one version.
    • Treating QIR as a human-readable format: it is compiler output; keep a higher-level source for review and editing.

    6.11 Quantum Simulators: Methods, Limits and GPUs¶

    Simulators run quantum circuits on ordinary computers, which is how almost all development and testing happens. A full state-vector simulator stores 2ⁿ complex numbers, so each added qubit doubles the memory: 30 qubits need 16 GiB, 40 qubits about 16 TiB. Specialised methods — stabiliser, tensor-network, matrix-product-state and density-matrix simulators — trade generality for much larger or noisier circuits.

    Think of it like…

    A state-vector simulator is like keeping a full spreadsheet of every possible lottery outcome — fine for a small lottery, impossible for a big one; tensor-network and stabiliser methods are clever shortcuts that work only when the lottery has hidden structure.

    Real-world example

    Farah, a PhD student, needs a 500-qubit GHZ state for a networking study. A state vector would need 2⁵⁰⁰ amplitudes — impossible — but Qiskit Aer's stabiliser method samples it in a fraction of a second because the circuit uses only H and CNOT, and the MPS method also succeeds because entanglement stays low. For a 28-qubit chemistry circuit with T gates she switches to a GPU state vector.

    How it works¶

    1. Classify the circuit: Clifford-only? low entanglement? noisy? number of qubits?
    2. Pick a method: stabiliser for Clifford, MPS/tensor network for low entanglement, state vector for general circuits up to ~30-40 qubits.
    3. Use density-matrix or trajectory (Monte Carlo) simulation when you need noise.
    4. Move to GPUs (cuQuantum, Aer GPU, lightning.gpu, CUDA-Q) or clusters when memory or speed limits bite.
    5. Validate small cases against an exact simulator before trusting approximate methods at scale.

    Who uses it

    Every quantum developer, plus HPC centres and researchers verifying 'quantum advantage' claims with classical simulation.

    Key takeaway

    Memorise: memory = 2ⁿ × 16 bytes for double-precision state vectors — 30 qubits = 16 GiB, 40 qubits = 16 TiB, 50 qubits = 16 PiB; density matrices square that (4ⁿ).

    Going deeper

    • Stabiliser simulators rely on the Gottesman-Knill theorem and Aaronson-Gottesman tableaus (2004), costing polynomial time; Stim and Aer's stabilizer method handle thousands of qubits, while 'extended stabiliser' methods add a few T gates at exponential cost in T-count.
    • Matrix product states store the state as a chain of tensors whose bond dimension grows with entanglement; they excel on 1D-like, shallow or low-entanglement circuits and were used to challenge several quantum-advantage claims.
    • Density-matrix simulation needs 4ⁿ entries (16 GiB at 15 qubits), so noisy simulation of larger circuits usually uses quantum trajectories: many state-vector runs with randomly sampled errors.
    • NVIDIA's cuQuantum SDK (cuStateVec, cuTensorNet, cuDensityMat; cuquantum-python 26.9 in 2026) accelerates Qiskit Aer, PennyLane Lightning, CUDA-Q, qsim and others; single-precision halves memory (8 bytes per amplitude).
    • Managed cloud simulators have published limits: Braket SV1 up to 34 qubits, DM1 17 qubits, TN1 50 qubits; Google says qsim reaches about 40 qubits on a 90-core workstation.

    Common mistakes & misconceptions

    • Believing 'a simulator can't do more than 50 qubits': for Clifford, low-entanglement or shallow circuits, specialised methods go far beyond.
    • Trusting a noiseless simulator's results as a hardware prediction: add a realistic noise model or fake backend before estimating real-device performance.
    • Running density-matrix simulations by default: they hit memory limits at about half the qubits of a state vector; use trajectories instead.

    Hannah, a project lead at fictional Northwind Bank, budgets a pilot: IBM's Pay-As-You-Go rate is $96 per QPU minute, so 100 experiments of about 6 seconds each cost about $960. The same 1,000-shot circuits on IonQ Forte via Braket would cost $80.30 each, or $8,030 in total, but on IQM Garnet only $175. She runs development on simulators and free tiers, then buys a small amount of the hardware that matches her technical needs.

    How it works¶

    1. Decide what hardware properties you need (qubit count, connectivity, fidelity, mid-circuit measurement).
    2. List providers offering that hardware and their billing units (seconds, shots, tasks, credits).
    3. Estimate usage: circuits × shots × repetitions, including error-mitigation overhead.
    4. Use free tiers, credits and simulators for development; reserve paid QPU time for final runs.
    5. Track spending with provider dashboards and cost tools; set budgets and alerts.

    Who uses it

    Project managers, researchers writing grant budgets, enterprise innovation teams and students looking for free access all need to understand quantum cloud pricing.

    Key takeaway

    Always convert prices to 'cost per useful result' — a cheaper but noisier device may need far more shots or mitigation to reach the same answer quality.

    Going deeper

    • IBM's 2026 prices: Open Plan free (10 minutes per 28 days), Pay-As-You-Go $96/minute billed per second, Flex $72/minute (400-minute minimum), Premium from $48/minute (5,200+ minutes a year), on-premises by quote.
    • Braket charges $0.30 per task plus device per-shot fees (e.g. IonQ Forte $0.08, IQM Garnet $0.00145, Rigetti Cepheus $0.000425) and offers hourly Braket Direct reservations from about $2,500 to $7,000 per hour depending on the device.
    • Quantinuum prices its machines in H-System Quantum Credits (HQCs), computed from gate and measurement counts, usually through subscriptions; IonQ and others sell direct cloud access alongside marketplace listings.
    • Google does not sell public access to its processors; in 2026 it ran a Willow Early Access Program for selected research proposals, while its software (Cirq, qsim, Stim) is freely available.
    • Dedicated and on-premises systems are a growing model: IBM Quantum System One/Two installations (e.g. at RIKEN and in Europe), and national centres buying their own machines for priority access and data sovereignty.

    Common mistakes & misconceptions

    • Comparing per-shot prices without considering fidelity: a device needing 10× more shots or heavy mitigation may cost more overall.
    • Forgetting mitigation and transpilation overhead in budgets: twirling and ZNE can multiply QPU time several-fold.
    • Leaving credentials or unrestricted keys in shared code: a leaked API key can spend your quantum budget like any cloud key.

    6.13 Your First Circuits: Bell, GHZ and Grover¶

    The fastest way to learn is to write and run tiny programs. A Bell circuit (H then CNOT) creates two perfectly correlated qubits; a GHZ circuit extends that to three or more; and Grover's search on two or three qubits finds a marked item with near-certainty after one or two steps. Each runs in seconds on a laptop and teaches circuits, measurement, shots and bit ordering.

    Think of it like…

    These circuits are the 'Hello, world!' programs of quantum computing — small enough to understand completely, but they exercise every part of the toolchain.

    Real-world example

    Zoe, a first-year student, runs a two-qubit Grover search that marks |11⟩: after one oracle and one diffuser, all 1,000 shots return '11'. She extends it to three qubits marking |101⟩; with two iterations the simulator returns '101' in 949 of 1,000 shots, close to the theoretical 94.5% success probability.

    How it works¶

    1. Bell: H on qubit 0, CNOT 0→1, measure — expect about 50% '00' and 50% '11', never '01' or '10'.
    2. GHZ: H on qubit 0, then a chain of CNOTs — expect only all-zeros or all-ones.
    3. Grover (2 qubits): H on both, oracle CZ marks |11⟩, diffuser (H, X, CZ, X, H), measure — '11' every time.
    4. Draw each circuit (qc.draw()) and check results against what theory predicts.
    5. Run on a noisy fake backend, then on real hardware, and compare how noise spreads results.

    Who uses it

    Every beginner, bootcamp and university course starts here; interviewers often ask candidates to write a Bell or GHZ circuit live.

    Key takeaway

    In Qiskit, qubit 0 is the rightmost character of a result bitstring — '01' means qubit 0 measured 1 and qubit 1 measured 0.

    Going deeper

    • Grover needs about (π/4)·√N iterations; for N = 4 one iteration gives exactly 100% success, while for N = 8 two iterations give sin²(5θ) ≈ 94.5% with θ = arcsin(1/√8) — more iterations would overshoot and reduce success.
    • Shot noise follows the binomial distribution: with 1,000 shots and p = 0.5, the standard deviation of the observed fraction is √(0.25/1000) ≈ 1.6%, so 470-530 '00' counts are entirely normal.
    • On real hardware a Bell circuit typically shows a few percent of '01' and '10' results from gate and readout errors; comparing ideal, fake-backend and hardware histograms teaches how noise appears.
    • Qiskit numbers qubits little-endian (qubit 0 on the right of bitstrings), while many textbooks and some SDKs write qubit 0 on the left — the most common beginner bug.
    • Visual tools help: IBM Quantum Composer lets you drag gates and see probabilities live, and qc.draw('mpl') or plot_histogram produce figures for reports.

    Common mistakes & misconceptions

    • Expecting identical counts every run: results are random samples; check that differences fit within shot noise.
    • Running too many Grover iterations: success probability oscillates, so the 'best' number is about (π/4)√N, not 'as many as possible'.
    • Reading Qiskit bitstrings left-to-right as qubit 0, 1, 2: they are written with the highest-index qubit first.

    Try it: Two-qubit Grover search for |11⟩ (pip install qiskit)¶

    from qiskit import QuantumCircuit
from qiskit.primitives import StatevectorSampler

qc = QuantumCircuit(2)
qc.h([0, 1])                 # uniform superposition
qc.cz(0, 1)                  # oracle: flip the phase of |11>
qc.h([0, 1]); qc.x([0, 1])   # diffuser: reflect about the mean
qc.cz(0, 1)
qc.x([0, 1]); qc.h([0, 1])
qc.measure_all()

print(qc.draw())
result = StatevectorSampler().run([qc], shots=1000).result()
print(result[0].data.meas.get_counts())   # {'11': 1000}

    6.14 Debugging, Testing, Benchmarking and Software Engineering¶

    Quantum programs are hard to debug because you cannot peek inside a running quantum computer and every result is random. Good practice is to test small pieces exactly on simulators, check that compilation didn't change the meaning of a circuit, test sampled results statistically, and benchmark with standard suites. Normal software engineering — version control, pinned dependencies, CI, code review and secret management — matters just as much as in any other field.

    Think of it like…

    Debugging a quantum program is like testing a recipe you can only taste after it's fully cooked, and only one random spoonful at a time — so you check each ingredient separately and taste many spoonfuls before judging.

    Real-world example

    Rohan, a software engineer at fictional Quanta Health, adds a pytest suite to his team's repository: one test compares the Bell state vector to the ideal, one checks the transpiled circuit has the same unitary, and one checks sampled counts with a 4-standard-deviation tolerance. CI runs them on every pull request in seven seconds, and they catch a bit-order bug before it reaches hardware.

    How it works¶

    1. Unit-test subcircuits exactly with Statevector or Operator equivalence on small sizes.
    2. Assert that transpilation preserves meaning (Operator.equiv on small circuits; compare output distributions on larger ones).
    3. Test sampled results statistically with fixed seeds and tolerances based on shot noise.
    4. Rehearse on noisy simulators or fake backends before using paid hardware.
    5. Benchmark with standard suites, log versions, job IDs and calibration data, and run tests in CI.

    Who uses it

    Quantum software engineers, SDK maintainers, research software engineers and QA teams in quantum companies; testing skills strongly distinguish job candidates.

    Key takeaway

    Treat every hardware result as data plus metadata: record SDK versions, backend name, calibration time, transpiler seed, shots and job ID — or you can't reproduce it.

    Going deeper

    • Exact checks scale only to roughly 20-30 qubits, so large programs are tested by composition: verify components exactly at small sizes, then check structural properties (gate counts, depth, qubit usage) and output distributions at scale.
    • Statistical tests should use tolerances tied to shot noise (e.g. 3-5 standard deviations) or tests such as chi-square and total-variation distance, with fixed seeds (seed_simulator, seed_transpiler) to avoid flaky CI.
    • Benchmark suites: QED-C's application-oriented benchmarks (20+ algorithm benchmarks scored with normalised Hellinger fidelity), SupermarQ (Super.tech, now Infleqtion), MQT Bench (Technical University of Munich) and IBM's Benchpress, which runs over 1,000 SDK performance tests on circuits up to 930 qubits.
    • Research on quantum software testing includes statistical assertions (Huang & Martonosi, 2019), projection-based runtime assertions (Li et al., 2020), mutation testing tools such as Muskit, and property-based testing with libraries like Hypothesis to generate random circuits.
    • Reproducibility needs pinned environments (requirements or lock files), stored compiled circuits (QPY), job IDs and backend calibration snapshots, because device noise changes daily and SDK APIs change between releases.

    Common mistakes & misconceptions

    • Testing sampled outputs with exact equality: random results make such tests fail intermittently; use tolerances and seeds.
    • Benchmarking SDKs or devices with a single favourite circuit: use a suite and report variance, because performance varies widely by circuit type.
    • Committing API tokens or account files to Git: store secrets in environment variables or secret managers and rotate them if leaked.

    Try it: A pytest suite for a quantum circuit (pip install qiskit pytest; run: pytest -q)¶

    from qiskit import QuantumCircuit
from qiskit.quantum_info import Statevector, Operator
from qiskit.transpiler import generate_preset_pass_manager
from qiskit.primitives import StatevectorSampler

def bell():
    qc = QuantumCircuit(2); qc.h(0); qc.cx(0, 1)
    return qc

def test_state_is_bell():
    assert Statevector(bell()).equiv(Statevector([1, 0, 0, 1]) / 2**0.5)

def test_transpiler_preserves_unitary():
    pm = generate_preset_pass_manager(optimization_level=3, basis_gates=["rz", "sx", "x", "cz"])
    assert Operator(pm.run(bell())).equiv(Operator(bell()))

def test_counts_are_balanced():
    qc = bell(); qc.measure_all()
    counts = StatevectorSampler(seed=42).run([qc], shots=4000).result()[0].data.meas.get_counts()
    assert set(counts) <= {"00", "11"}
    assert abs(counts["00"] / 4000 - 0.5) < 0.03     # about 4 standard deviations
