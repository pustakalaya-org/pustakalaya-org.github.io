    Chapter 3: Data Modelling & Database Design¶

    Before any data is stored, someone has to decide what the tables, documents and keys should look like. This chapter walks from requirements to conceptual, logical and physical models; ER diagrams, keys and modern ID choices; functional dependencies and every normal form with worked examples; when to denormalise; dimensional modelling, slowly changing dimensions, Kimball, Inmon and Data Vault for analytics; access-pattern-first modelling for NoSQL; safe schema migrations; naming conventions, classic anti-patterns and choosing data types well.

    3.1 From Requirements to Conceptual, Logical and Physical Models¶

    Database design turns a plain-language description of a business into tables a computer can store. Designers work in three levels: a conceptual model (the things and how they relate), a logical model (tables, columns and keys, independent of any product) and a physical model (the exact database product, data types, indexes and storage).

    Think of it like…

    It is like building a house: first a napkin sketch of rooms and how they connect, then a measured floor plan, and finally the builder's construction drawings that name the exact bricks, pipes and wiring.

    Real-world example

    Amara designs a loans system for the fictional Greenleaf Libraries. Interviews give her nouns (member, book, copy, branch, loan) and rules ("a member may hold at most 5 loans"). Her conceptual ER diagram shows Member borrows Copy. The logical model adds keys and normalises to 3NF. The physical model picks PostgreSQL, a date column for due_date, an index on (member_id, returned_at) and a CHECK on loan length.

    How it works¶

    1. Gather requirements: interview users, collect forms, reports and the questions the system must answer, and write down business rules.
    2. Build a conceptual model: identify entities, relationships and cardinalities in an ER diagram that business people can read.
    3. Build a logical model: add attributes, primary and foreign keys, and normalise (usually to 3NF) without choosing a product.
    4. Build a physical model: map to a specific DBMS with data types, constraints, indexes, partitioning and naming conventions.
    5. Validate with sample data and the real queries, review with stakeholders, then generate DDL and manage later changes as migrations.

    Who uses it

    Data modellers, data architects, backend developers, analytics engineers and DBAs all design or review models; business analysts help capture the requirements.

    Key takeaway

    Memorise the one-liner: conceptual = what the business cares about, logical = how it is structured independent of product, physical = how one specific DBMS will store it.

    Going deeper

    • The ANSI/SPARC three-schema architecture (1975-78) separates external views, a conceptual schema and an internal storage schema, so applications survive storage changes; this is the idea of data independence.
    • Business rules become structure: "each loan is for exactly one copy" is a cardinality, "at most 5 open loans" needs a trigger or application check, and "due within 28 days" becomes a CHECK constraint.
    • Physical design depends on the workload: estimate row counts, growth per year, the read/write ratio and the top ten queries, because indexes and partitioning are chosen for those queries, not for the diagram.
    • Modelling tools forward-engineer a diagram into DDL and reverse-engineer an existing database into a diagram; comparing the two reveals drift between documentation and reality.
    • A data dictionary or business glossary records each column's meaning, unit, allowed values and owner, which later feeds data catalogs and governance tools in the analytics world.

    Common mistakes & misconceptions

    • Jumping straight to CREATE TABLE: skipping the conceptual model hides misunderstood rules until data is already wrong.
    • Designing without the queries: a model that ignores how data will be read often needs painful redesign or heavy denormalisation later.
    • Treating the model as finished: requirements change, so plan for versioned migrations rather than a one-time design document.

    Try it: A tiny physical model for the library example (PostgreSQL)¶

    CREATE TABLE member (
  member_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      text NOT NULL UNIQUE,
  full_name  text NOT NULL
);
CREATE TABLE loan (
  loan_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  member_id   bigint NOT NULL REFERENCES member,
  copy_id     bigint NOT NULL,
  loaned_at   date NOT NULL DEFAULT current_date,
  due_at      date NOT NULL,
  returned_at date,
  CHECK (due_at <= loaned_at + 28)
);
CREATE INDEX ON loan (member_id) WHERE returned_at IS NULL;

    3.2 ER Diagrams: Entities, Relationships, Cardinality and Notations¶

    An Entity-Relationship (ER) diagram is a drawing of the things a business tracks (entities), their properties (attributes) and how they connect (relationships). Symbols on the lines show cardinality — how many of one thing can link to another — and whether the link is optional. Several drawing styles exist; crow's foot is the most common in industry, Chen in textbooks, UML in software design.

    Three ER notations side by side

    Chen (1976) Crow's foot UML class diagram
    Entity Rectangle Rectangle with attribute list Class box
    Relationship Diamond with verb Labelled line Association line
    "Many" end N or M beside line Three-pronged foot * or 0..*
    Optional end Single line (partial) Circle (O) 0..1 or 0..*
    Weak entity Double rectangle Key includes parent FK Composition (filled diamond)
    Typical use Textbooks, exams Industry tools Software design

    Same ideas, different symbols: learn crow's foot for work and Chen for exams.

    Think of it like…

    An ER diagram is like a family tree for data: boxes for people, lines for relationships, and little marks that say "exactly one mother" or "zero or more children".

    Real-world example

    Kwame models the fictional Ridgeway Clinic. Patient and Doctor are entities; Appointment links them many-to-many with a date and room. A Prescription has Prescription Lines that cannot exist without it, so each line is a weak entity identified by prescription number plus line number. Crow's foot marks show a patient may have zero or many appointments, but each appointment has exactly one patient.

    How it works¶

    1. List the nouns that matter to the business; each becomes a candidate entity with attributes.
    2. Connect entities with verb-named relationships (Patient books Appointment).
    3. Set cardinality (1:1, 1:N, M:N) and optionality (minimum 0 or 1) at both ends of each line.
    4. Resolve many-to-many relationships into an associative entity that carries the relationship's own attributes.
    5. Mark weak entities, identifying relationships and any subtype/supertype hierarchies, then review the diagram with business users.

    Who uses it

    Students in every database course, data modellers, solution architects and backend developers drawing schemas for design reviews.

    Key takeaway

    Read each line in both directions as a sentence ("each order has one or more lines; each line belongs to exactly one order") — interviewers often ask you to do this out loud.

    Going deeper

    • Peter Chen's 1976 paper in ACM Transactions on Database Systems introduced the ER model; crow's foot notation is usually credited to Gordon Everest (1976) and spread through Oracle's Barker notation and CASE tools.
    • Attributes come in kinds: simple vs composite (address = street + city), single- vs multivalued (phone numbers), stored vs derived (age from birth date); multivalued attributes become separate tables in the logical model.
    • Min-max notation such as (0,N) or (1,1) states both participation and cardinality precisely and avoids confusion about which end of the line a symbol describes.
    • Ternary relationships (Supplier supplies Part to Project) cannot always be replaced by three binary ones without losing meaning, which links directly to fifth normal form.
    • Enhanced ER adds specialisation: a Vehicle supertype with Car and Truck subtypes, marked disjoint or overlapping and total or partial; these map to single-table, table-per-type or table-per-subclass designs.
    • IDEF1X, published as US federal standard FIPS 184 in 1993, distinguishes identifying (solid) and non-identifying (dashed) relationships and is still offered by tools such as erwin.

    Common mistakes & misconceptions

    • Leaving many-to-many relationships unresolved: relational tables cannot store M:N directly, so you need a junction table with two foreign keys.
    • Reading cardinality at the wrong end: in crow's foot the symbol nearest an entity describes how many of that entity relate to one on the other side.
    • Modelling reports instead of things: "Monthly Sales Report" is an output, not an entity; model the underlying sales and derive the report.

    3.3 Keys and Identifiers: Natural, Surrogate, bigint, UUIDv4 and UUIDv7¶

    A key is a column, or set of columns, whose values identify each row uniquely. A table may have several candidate keys; one becomes the primary key, and other tables point to it with foreign keys. You can use a real-world value (a natural key such as an ISBN) or an invented one (a surrogate key such as an auto-numbered bigint or a UUID).

    bigint identity vs UUIDv4 vs UUIDv7

    bigint identity UUIDv4 UUIDv7
    Size 8 bytes 16 bytes 16 bytes
    Generated by Database sequence Anyone, anywhere Anyone, anywhere
    Order Increasing Random Time-ordered (ms)
    B-tree inserts Append at right edge Random page splits Mostly append
    Guessable / leaks Counts rows, guessable Not guessable Reveals creation time
    Bits of randomness None 122 Up to 74

    UUIDv7 keeps UUID's generate-anywhere benefit while restoring index locality.

    Think of it like…

    A natural key is like identifying people by passport number, which can change or be missing; a surrogate key is like a membership card number your gym prints for you — meaningless, but stable and always present.

    Real-world example

    Ola builds the fictional ParcelHop delivery app. Customers get a bigint identity primary key, with email as a UNIQUE alternate key because people change emails. Parcels are created on phones offline, so they use UUIDv7 IDs generated on the device; because UUIDv7 starts with a timestamp, new rows still land at the end of the index instead of scattering across it.

    How it works¶

    1. List candidate keys: minimal column sets that are unique and never null for every possible row.
    2. Pick a primary key that is unique, never null, stable over time and compact — often a surrogate.
    3. Keep natural candidate keys enforced with UNIQUE constraints so duplicates are still rejected.
    4. Add foreign keys in child tables, choose ON DELETE/ON UPDATE actions, and index FK columns that are used in joins.
    5. Choose an ID generator: database identity/sequence for single databases, UUIDv7 or Snowflake-style IDs for distributed or client-side generation.

    Who uses it

    Every backend developer, data modeller and DBA chooses keys; ID strategy is a classic system-design interview topic.

    Key takeaway

    Say it this way: a surrogate primary key plus UNIQUE constraints on natural keys gives stability and data quality; choose UUIDv7 over UUIDv4 when IDs must be generated outside the database.

    Going deeper

    • RFC 9562 (May 2024) replaced RFC 4122 and defined UUID versions 6, 7 and 8; UUIDv7 puts a 48-bit Unix millisecond timestamp first, then version and variant bits, then random or counter bits.
    • In MySQL InnoDB the table is stored in primary-key order (a clustered index), so random UUIDv4 keys cause page splits, half-empty pages and extra buffer-pool misses; PostgreSQL B-tree indexes on UUIDv4 suffer similarly.
    • PostgreSQL 18 (September 2025) added a built-in uuidv7() function; store UUIDs in a native 16-byte uuid or BINARY(16) column, never as CHAR(36) text that takes more than twice the space.
    • A signed bigint tops out at 9,223,372,036,854,775,807, effectively inexhaustible, while a 32-bit int stops at 2,147,483,647 — a limit real products have hit, forcing emergency migrations.
    • Twitter's 2010 Snowflake format packs a 41-bit millisecond timestamp, a 10-bit machine ID and a 12-bit sequence into 64 bits, allowing 4,096 IDs per millisecond per machine without coordination.
    • Foreign-key actions — CASCADE, SET NULL, SET DEFAULT, RESTRICT and NO ACTION — decide what happens to children when a parent changes; PostgreSQL does not auto-index FK columns, whereas InnoDB requires and creates one.

    Common mistakes & misconceptions

    • Using a mutable natural key like email as the primary key: every change must cascade through all child tables; use a surrogate and keep email UNIQUE.
    • Exposing sequential IDs in public URLs: competitors can count your orders; use UUIDs or a separate random public identifier.
    • Storing UUIDs as varchar: it wastes space, slows comparisons and invites case and format mismatches; use the native uuid or 16-byte binary type.

    Open specification (ulid/spec) · Format · Current · Intermediate · General    		 128-bit sortable ID: 48-bit millisecond timestamp plus 80 random bits, written as 26 Crockford Base32 characters. An event log uses 01J... ULIDs so files sorted by name are also sorted by time.

    API design practice · Pattern · Current · Intermediate · General    		 A separate random, non-guessable ID exposed in URLs and APIs, while the internal bigint key stays private. Orders are shown as /orders/ord_7Fq2kZ9x while joins use order_id 1048576 internally.

    3.4 Functional Dependencies and Update Anomalies¶

    A functional dependency (FD) says that knowing one value fixes another: if you know a student ID, you know the student's name. Writing these rules down shows where the same fact is stored many times. Redundancy causes anomalies — you cannot insert, update or delete one fact without disturbing another — and normalisation removes them using FDs.

    Think of it like…

    A postcode determines the town: if a spreadsheet repeats the town next to every customer's postcode, sooner or later someone types the town wrong in one row and the sheet contradicts itself.

    Real-world example

    The fictional Northgate College keeps one wide Enrolment sheet: student_id, student_name, course_id, course_title, lecturer_id, lecturer_name, grade. Because course_id determines course_title, the title is repeated 300 times; renaming a course means 300 updates. A new course cannot be added until a student enrols, and when the last student withdraws, the lecturer's name disappears too.

    How it works¶

    1. List the attributes of the table and ask, for each pair, "if I know X, is Y always fixed?" using business rules, not just current data.
    2. Write FDs as X → Y (student_id → student_name; {student_id, course_id} → grade).
    3. Compute attribute closures (everything determined by X) to find candidate keys.
    4. Spot partial dependencies (on part of a composite key) and transitive ones (through a non-key attribute).
    5. Decompose the table so each FD's left side is a key, checking the split is lossless and preserves dependencies.

    Who uses it

    Database students (FDs are on every exam), data modellers fixing messy legacy tables, and data engineers profiling data quality.

    Key takeaway

    Memorise the three anomalies — insertion, update, deletion — and be ready to show each on a small example table; it is the standard way to motivate normalisation.

    Going deeper

    • Armstrong's axioms (1974) — reflexivity, augmentation and transitivity — are sound and complete: every FD implied by a set can be derived with them, plus derived rules for union, decomposition and pseudo-transitivity.
    • The closure X+ is computed by repeatedly adding attributes determined by what you already have; if X+ contains every attribute of the table, X is a superkey, and if no proper subset is, X is a candidate key.
    • A minimal (canonical) cover rewrites a set of FDs with single attributes on the right, no redundant FDs and no extraneous left-side attributes; 3NF synthesis algorithms start from it.
    • Data can disprove an FD but never prove it: a table where course_id currently determines title may still allow two titles tomorrow, so FDs come from business rules, while data profiling tools only suggest candidates.
    • Heath's theorem (1971) says that if X → Y holds in R(X, Y, Z), splitting into (X, Y) and (X, Z) is lossless; in general a binary split is lossless when the shared columns are a key of one side.

    Common mistakes & misconceptions

    • Reading an FD backwards: student_id → name does not mean name → student_id; two students can share a name.
    • Inferring FDs from a small sample: coincidences in 50 rows are not rules; confirm each dependency with the business owner.
    • Decomposing without checking losslessness: a bad split creates spurious rows when you join the pieces back together.

    Try it: Test whether an FD (course_id → course_title) actually holds in your data¶

       COUNT(DISTINCT course_title) AS titles,

FROM enrolment_raw

    3.5 Normalisation Step by Step: 1NF, 2NF and 3NF¶

    Normalisation is a step-by-step method for splitting tables so that each fact is stored once. First normal form (1NF) means one value per cell and no repeating groups; 2NF removes facts that depend on only part of a composite key; 3NF removes facts that depend on other non-key columns. Most business (OLTP) databases are designed to at least 3NF.

    Think of it like…

    It is like tidying a messy drawer into labelled boxes: socks in one, chargers in another — you always know where each thing lives, and you never have to update two boxes when one thing changes.

    Real-world example

    The fictional Bluebird Bakery tracks orders in a sheet: order 77, 2026-03-02, customer C9 'Tomás Ruiz', 'Leeds', products 'Croissant×2, Bagel×1'. 1NF: one row per product line with key (order_id, product_id). 2NF: order_date and customer_id move to Orders; product name and list price move to Products. 3NF: customer name and city move to Customers, because they depend on customer_id, not on the order.

    How it works¶

    1. Start from the unnormalised data and identify repeating groups and multi-value cells.
    2. 1NF: make every cell atomic, give each row a primary key, and turn repeating groups into separate rows.
    3. 2NF: for composite keys, move attributes that depend on only part of the key into their own table.
    4. 3NF: move attributes that depend on another non-key attribute (transitive dependencies) into their own table.
    5. Re-link the tables with foreign keys and check the joins reproduce the original data (lossless).

    Who uses it

    Every database student, backend developer designing OLTP schemas, and interviewer asking "normalise this table" on a whiteboard.

    Key takeaway

    Memorise Bill Kent's summary: every non-key attribute must depend on the key (1NF), the whole key (2NF) and nothing but the key (3NF).

    Going deeper

    • Codd defined 1NF in 1970 and 2NF and 3NF in 1971; Bill Kent's 1983 Communications of the ACM article "A Simple Guide to Five Normal Forms" remains the clearest short explanation.
    • Formally, a table is in 3NF if for every non-trivial FD X → A, either X is a superkey or A is part of some candidate key (a prime attribute) — the second clause is what separates 3NF from BCNF.
    • 2NF only matters when a table has a composite candidate key; a table whose only key is a single column and which satisfies 1NF is automatically in 2NF.
    • Storing unit_price on order_line is not a 3NF violation: it records the price actually charged on that date, a different fact from the product's current list price.
    • Bernstein's 1976 synthesis algorithm builds a 3NF schema from a minimal cover that is always lossless and dependency-preserving, which is why 3NF is the practical target for most OLTP designs.
    • "Atomic" is relative: C. J. Date argues arrays or JSON can satisfy 1NF if treated as single values; the practical test is whether you will search, join or constrain the parts — if so, split them.

    Common mistakes & misconceptions

    • Thinking 1NF just means no commas: columns like phone1, phone2, phone3 are still a repeating group and belong in a separate table.
    • Over-normalising lookups: splitting every short code into its own table can add joins without removing any real redundancy.
    • Moving historical values out by mistake: an invoice's address at time of sale must be copied and kept, not replaced by a link to the current address.

    Try it: Bluebird Bakery in 3NF (works in PostgreSQL, MySQL and SQLite with small type tweaks)¶

    CREATE TABLE customer (customer_id int PRIMARY KEY, full_name text NOT NULL, city text NOT NULL);
CREATE TABLE product  (product_id  int PRIMARY KEY, name text NOT NULL, list_price numeric(8,2) NOT NULL);
CREATE TABLE orders   (order_id    int PRIMARY KEY, order_date date NOT NULL,
                       customer_id int NOT NULL REFERENCES customer);
CREATE TABLE order_line (
  order_id   int REFERENCES orders,
  product_id int REFERENCES product,
  qty        int NOT NULL CHECK (qty > 0),
  unit_price numeric(8,2) NOT NULL,   -- price actually charged
  PRIMARY KEY (order_id, product_id)
);

    3.6 Beyond 3NF: BCNF, 4NF, 5NF and 6NF¶

    Higher normal forms deal with rarer kinds of redundancy that 3NF misses. Boyce-Codd normal form (BCNF) requires every determinant to be a candidate key. Fourth normal form removes independent multi-valued facts stored together, and fifth normal form removes redundancy that only appears when three or more relationships are combined. Sixth normal form splits tables down to one fact per row and is used for history-heavy warehouses.

    Think of it like…

    If 3NF is tidying the drawer into boxes, the higher forms are checking that no box secretly contains two unrelated collections taped together — rare in a normal house, but it matters in a museum archive.

    Real-world example

    At the fictional Oakfield Tutoring centre each tutor teaches exactly one subject, and each student has one tutor per subject. The table Tutoring(student, subject, tutor) is in 3NF but not BCNF, because tutor → subject while tutor is not a key. Splitting into TutorSubject(tutor, subject) and StudentTutor(student, tutor) removes the redundancy, but the rule "one tutor per subject per student" now needs a trigger.

    How it works¶

    1. Check BCNF: for every non-trivial FD X → Y, X must be a superkey; if not, split on that FD.
    2. Check 4NF: look for independent multi-valued facts (course →→ teacher, course →→ textbook) in one table and separate them.
    3. Check 5NF: if a table can be rebuilt only from three or more projections (a cyclic business rule), decompose into those projections.
    4. Decide whether to accept 3NF instead of BCNF when the split would lose a dependency you must enforce.
    5. For temporal warehouses, consider 6NF-style tables (one attribute plus time per table) when attributes change at different rates.

    Who uses it

    Database theory students, data architects reviewing complex enterprise models, and warehouse designers using anchor or Data Vault models.

    Key takeaway

    Know the textbook BCNF counter-example (student, subject, tutor) and the fact that 3NF can always be reached without losing dependencies, while BCNF sometimes cannot.

    Going deeper

    • BCNF was defined by Raymond Boyce and Edgar Codd in 1974; it differs from 3NF only when a table has overlapping composite candidate keys, which is why most 3NF tables are already in BCNF.
    • Ronald Fagin introduced 4NF (1977) using multivalued dependencies, 5NF or project-join normal form (1979) using join dependencies, and domain-key normal form (1981), which expresses all constraints through domains and keys.
    • A classic 5NF case: if a supplier supplies a part, the supplier serves a project and the project uses the part, then the supplier supplies that part to that project; storing all three pairs separately is then lossless.
    • Sixth normal form, defined by Date, Darwen and Lorentzos (2002) for temporal data, allows only a key plus at most one other attribute; anchor modelling (2009) and parts of Data Vault apply the idea.
    • Essential tuple normal form (Darwen, Date and Fagin, 2012) sits between BCNF and 5NF and targets exactly the redundancy that causes duplicated tuples, giving a more practical goal than 5NF.

    Common mistakes & misconceptions

    • Assuming higher is always better: chasing 5NF or 6NF in an OLTP app adds many joins for redundancy that may never occur.
    • Forgetting lost dependencies: a BCNF split can make a business rule unenforceable by keys alone, so add a constraint, trigger or stay in 3NF.
    • Confusing 4NF problems with bad 1NF fixes: flattening two independent lists into one table creates the cross-product rows that 4NF removes.

    3.7 Denormalisation: Breaking the Rules on Purpose¶

    Denormalisation means deliberately storing some data more than once, or storing pre-computed results, so that important reads are faster or simpler. You pay for it with extra work on every write and the risk that copies drift apart. It should be a measured decision after indexes, better queries and caching have been tried — not a starting point.

    Normalised vs denormalised design

    Normalised (3NF) Denormalised
    Each fact stored Once Several times
    Reads More joins Fewer joins, faster
    Writes Touch one row Touch every copy
    Consistency risk Low Copies can drift
    Storage Smaller Larger
    Best fit OLTP, money, stock Read-heavy pages, analytics

    Denormalisation moves cost from reads to writes and adds a consistency job.

    Think of it like…

    It is like writing a friend's phone number in both your phone and on the fridge: quicker to find when you need it, but if they change numbers you must remember to update both.

    Real-world example

    The fictional ShopLane marketplace shows product cards with star ratings. Computing AVG(rating) over 40 million reviews per page took 120 ms. The team added review_count and rating_avg columns on product, updated by the review service in the same transaction, cutting the card query to 3 ms. A nightly job recomputes both columns and alerts if any product drifts.

    How it works¶

    1. Measure first: find the slow query with EXPLAIN and real timings, and try indexes, rewrites and caching.
    2. Choose the smallest denormalisation that fixes it: a copied column, a counter, a summary table or a materialized view.
    3. Pick a single source of truth and one mechanism that maintains the copy (same transaction, trigger, refresh job or event).
    4. Decide the acceptable staleness: synchronous for money and stock, seconds or hours for dashboards.
    5. Add reconciliation checks and document the duplicate so future developers know it must be kept in sync.

    Who uses it

    Backend developers tuning hot pages, analytics engineers building reporting tables, and architects designing read-heavy systems.

    Key takeaway

    Quote the saying "normalise until it hurts, denormalise until it works" — then explain how you would keep the copies consistent; that second part is what interviewers want.

    Going deeper

    • Every copy needs exactly one owner and one maintenance path; the classic failure is two code paths updating the same duplicated column differently, which no constraint will catch.
    • Counter columns on hot rows create lock contention: 5,000 likes per second on one post serialise on a single row, so high-traffic systems batch increments or shard counters across several rows.
    • PostgreSQL materialized views refresh fully; REFRESH MATERIALIZED VIEW CONCURRENTLY avoids blocking readers but needs a unique index, and incremental maintenance requires extensions such as pg_ivm.
    • SQL Server indexed views and Oracle fast-refresh materialized views (using materialized view logs) maintain aggregates automatically, trading write overhead for instant reads.
    • Generated columns are a safe, database-maintained form of denormalisation; PostgreSQL 18 made virtual (computed-on-read) generated columns the default, while STORED ones are computed on write and can be indexed.

    Common mistakes & misconceptions

    • Denormalising before measuring: many slow queries are fixed by one missing index, with no duplicate data to maintain.
    • No reconciliation: without a periodic check, drifted counters and stale copies go unnoticed until a customer complains.
    • Copying data that changes often: duplicating a frequently updated value multiplies write load and lock contention.

    Try it: A trigger-maintained counter column (PostgreSQL)¶

    ALTER TABLE product ADD COLUMN review_count int NOT NULL DEFAULT 0;

CREATE FUNCTION bump_review_count() RETURNS trigger AS $$
BEGIN
  UPDATE product SET review_count = review_count + 1
  WHERE product_id = NEW.product_id;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER review_ai AFTER INSERT ON review
FOR EACH ROW EXECUTE FUNCTION bump_review_count();

    3.8 Dimensional Modelling: Facts, Dimensions, Star and Snowflake Schemas¶

    Dimensional modelling designs databases for analysis rather than for running the business. Measurements such as sales amounts go in a central fact table; the descriptive context — date, store, product, customer — goes in surrounding dimension tables. Drawn out, it looks like a star. It makes reports simple to write and fast to run.

    Think of it like…

    A fact table is a till receipt roll — long, narrow and full of numbers; dimensions are the reference books you look things up in: the calendar, the store directory and the product catalogue.

    Real-world example

    The fictional Sunrise Grocers has 120 stores and about 40 million receipt lines a year. Fact_sales has one row per receipt line with quantity, net amount and discount, plus keys to Dim_date, Dim_store, Dim_product, Dim_customer and Dim_promotion. Analysts ask "revenue by region by month for organic products" with simple joins and GROUP BY, and the columnar warehouse answers in under a second.

    How it works¶

    1. Choose the business process to model, such as retail sales, shipments or call-centre calls.
    2. Declare the grain: exactly what one fact row represents (one receipt line, one daily balance).
    3. Identify the dimensions that describe each fact: who, what, where, when, how.
    4. Identify the numeric facts (measures) and whether each is additive, semi-additive or non-additive.
    5. Connect processes through conformed dimensions on an enterprise bus matrix so reports can combine them.

    Who uses it

    BI developers, analytics engineers, data warehouse architects and data analysts who write reporting SQL every day.

    Key takeaway

    Always state the grain first; most dimensional-modelling mistakes in interviews come from mixing facts at different grains in one table.

    Going deeper

    • Ralph Kimball and Margy Ross's The Data Warehouse Toolkit (3rd edition, 2013) defines the four-step process — business process, grain, dimensions, facts — and the vocabulary used across the industry.
    • Fact tables are deep and narrow (billions of rows of keys and numbers); dimension tables are wide and shallow (dozens of descriptive columns, thousands to millions of rows).
    • Dimensions use integer surrogate keys rather than source-system IDs, which insulates the warehouse from source changes and enables slowly changing dimension history.
    • Semi-additive measures such as account balances or stock on hand can be summed across stores but not across time; use averages or period-end values over dates instead.
    • Columnar warehouses compress repetitive dimension keys extremely well and optimisers recognise star joins, so star schemas remain efficient on Snowflake, BigQuery, Redshift and ClickHouse.

    Common mistakes & misconceptions

    • Mixing grains: putting order-level shipping cost on every order line inflates totals when summed; allocate it or use a separate fact table.
    • Snowflaking by habit: normalising dimensions saves little space and forces analysts to write more joins for no real gain.
    • Using source-system keys directly: when the source recycles or changes IDs, history in the warehouse silently breaks.

    Try it: A typical star-schema query¶

    SELECT d.year_month, s.region, SUM(f.net_amount) AS revenue
FROM   fact_sales  f
JOIN   dim_date    d ON d.date_key    = f.date_key
JOIN   dim_store   s ON s.store_key   = f.store_key
JOIN   dim_product p ON p.product_key = f.product_key
WHERE  p.is_organic AND d.year = 2026
GROUP  BY d.year_month, s.region
ORDER  BY d.year_month, revenue DESC;

    3.9 Slowly Changing Dimensions and Keeping History¶

    Descriptive data changes over time: customers move, products change category, staff change teams. Slowly changing dimension (SCD) types are standard recipes for what a warehouse does when that happens — overwrite, add a new versioned row, or keep the old value in a spare column. Operational databases have their own history tools, such as SQL:2011 temporal tables.

    Grace moves from Lagos to Abuja

    Type 1 overwrite Type 2 new row Type 3 extra column
    After the move city = Abuja Old row closed, new row Abuja city = Abuja, prev_city = Lagos
    Rows for Grace 1 2 1
    History kept None Full One previous value
    Old sales report as Abuja (restated) Lagos (as it was) Either, by choice
    Typical use Typo fixes Region, segment, tier Planned reorganisations

    Only Type 2 keeps old sales attached to the old city automatically.

    Think of it like…

    SCD Type 1 is correcting a pencil entry with an eraser; Type 2 is a passport stamp book where each new stamp is added and the old ones stay visible; Type 3 is writing "previously: …" next to the current entry.

    Real-world example

    Customer 5512, Grace Okafor, moves from Lagos to Abuja on 2026-06-01. With SCD Type 2, the warehouse closes her old row (valid_to 2026-05-31, is_current false) and inserts a new row with a new surrogate key for Abuja. Sales before June still roll up to Lagos, and sales after it to Abuja, so regional reports stay historically correct.

    How it works¶

    1. Decide per attribute whether history matters: a typo fix needs none, a change of region usually does.
    2. Type 1: overwrite in place; Type 2: expire the current row and insert a new version with a new surrogate key.
    3. Track validity with valid_from, valid_to and an is_current flag, and load facts with the key valid at the event date.
    4. Use MERGE or a tool such as dbt snapshots to detect changed source rows and apply the chosen type.
    5. In OLTP systems, use system-versioned temporal tables or audit tables to answer "what did this row look like on date X?"

    Who uses it

    Data warehouse developers, analytics engineers using dbt, auditors and anyone in regulated industries who must reproduce past reports.

    Key takeaway

    Be able to explain Types 0, 1, 2 and 3 in one sentence each, and know that Type 2 is the default for attributes used to group historical reports.

    Going deeper

    • Kimball's catalogue runs from Type 0 (never change) to Types 1, 2, 3, 4 (mini-dimension for fast-changing attributes), 5, 6 (1+2+3 hybrid) and 7; other authors use Type 4 for a separate history table, so define terms in design documents.
    • SQL:2011 added temporal features: system-versioned tables record when rows were stored (transaction time), while application-time periods record when facts were true in the real world (valid time).
    • SQL Server (2016), MariaDB (10.3) and Db2 support system-versioned tables queried with FOR SYSTEM_TIME AS OF; Oracle offers Flashback Query, and PostgreSQL relies on triggers or extensions.
    • PostgreSQL 18 added temporal constraints: PRIMARY KEY and UNIQUE with WITHOUT OVERLAPS on a range column, and foreign keys with PERIOD, so overlapping validity periods can be rejected by the database.
    • Bitemporal models store both valid time and transaction time, answering "what did we believe on 1 March about Grace's address on 1 February?" — essential for insurance, finance and regulatory reporting.

    Common mistakes & misconceptions

    • Joining facts to the current dimension row only: Type 2 needs the version valid at the event date, or history is silently restated.
    • Using NULL as an open-ended valid_to: BETWEEN filters then miss current rows; many teams use 9999-12-31 instead.
    • Tracking every column as Type 2: fast-changing attributes explode row counts; use Type 1 or a mini-dimension for them.

    Try it: SCD Type 2 in two statements (PostgreSQL)¶

    -- 1. expire the current version when the city changed
UPDATE dim_customer d SET valid_to = current_date - 1, is_current = false
FROM   stg_customer s
WHERE  d.customer_id = s.customer_id AND d.is_current AND d.city <> s.city;

-- 2. insert a new current version for new or changed customers
INSERT INTO dim_customer (customer_id, full_name, city, valid_from, valid_to, is_current)
SELECT s.customer_id, s.full_name, s.city, current_date, DATE '9999-12-31', true
FROM   stg_customer s
LEFT JOIN dim_customer d ON d.customer_id = s.customer_id AND d.is_current
WHERE  d.customer_id IS NULL;

    3.10 Kimball vs Inmon vs Data Vault¶

    There are three classic ways to organise an enterprise data warehouse. Kimball builds business-friendly star schemas process by process. Inmon builds a central, normalised (3NF) enterprise warehouse first, then feeds data marts from it. Data Vault stores raw history in hubs, links and satellites that are easy to extend and audit, then publishes star schemas on top.

    Think of it like…

    Kimball builds a town one useful shop at a time with a shared street plan; Inmon designs the whole city grid before opening any shop; Data Vault builds a giant, well-labelled warehouse of every delivery ever received, then sets up shop fronts from it.

    Real-world example

    The fictional Meridian Bank merges three acquired lenders, each with different customer systems. It loads all three into a Data Vault: Hub_Customer holds business keys, Link_Customer_Account connects customers and accounts, and satellites keep every attribute change with load timestamps. Analysts never query the vault directly; dbt builds Kimball-style star schemas for lending and risk on top of it.

    How it works¶

    1. Clarify the goal: fast business delivery (Kimball), a single integrated enterprise model (Inmon) or auditable, extensible raw history (Data Vault).
    2. Land source data in staging, keeping raw copies for reprocessing.
    3. Integrate: conform dimensions (Kimball), model the enterprise in 3NF (Inmon) or load hubs, links and satellites (Data Vault).
    4. Apply business rules in a separate layer (business vault or transformation models) so raw history stays untouched.
    5. Publish star schemas or wide tables for BI tools and analysts.

    Who uses it

    Data warehouse architects, analytics engineers, BI teams and consultants in banking, insurance, retail and government.

    Key takeaway

    A safe interview answer: most modern teams mix them — a raw or Data Vault integration layer for history, and Kimball star schemas for consumption.

    Going deeper

    • Bill Inmon's Building the Data Warehouse (1992) defined the warehouse as subject-oriented, integrated, time-variant and non-volatile; his Corporate Information Factory places a 3NF enterprise warehouse before departmental marts.
    • Kimball's bus architecture delivers one business process at a time, with conformed dimensions guaranteeing that separately built stars still fit together into an enterprise view.
    • Dan Linstedt released Data Vault in 2000; Data Vault 2.0, described in his 2015 book with Michael Olschimke, adds hash keys, a methodology and agile delivery guidance.
    • Data Vault 2.0 hashes business keys (often MD5 or SHA-1, hex-encoded) so hubs, links and satellites can load in parallel without waiting for sequence lookups, and uses hash_diff columns to detect changed attributes.
    • Point-in-time (PIT) tables record which satellite row was current for each key on each snapshot date, and bridge tables pre-join hubs and links, making vault queries far cheaper.
    • Cloud warehouses and dbt packages such as AutomateDV and datavault4dbt have made Data Vault loading largely code-generated, while some teams skip it in favour of simpler wide tables.

    Common mistakes & misconceptions

    • Letting analysts query the raw vault: the many joins make it slow and confusing; always publish marts or views for consumption.
    • Choosing Inmon's big up-front model for a small team: months pass before anyone gets a report, and sponsors lose interest.
    • Treating the methods as rivals: hybrids are normal, and the right mix depends on source volatility, audit needs and team size.

    3.11 Modelling for NoSQL: Access Patterns First¶

    Relational design starts from the data and lets queries be anything later. NoSQL design usually works the other way round: list every question the application will ask, then shape documents or keys so each question is answered by one fast lookup. You decide what to embed together, what to reference, and how to name keys so related items sit side by side.

    Three ways to design the same app

    Relational Document (MongoDB) Key-value (DynamoDB)
    Design starts from Entities and normal forms Access patterns Access patterns
    Related data Joined at query time Embedded or referenced Pre-grouped by key
    Duplication Avoided Accepted where useful Common
    New query type Usually just SQL May need new index May need new GSI or remodel
    Size limit per unit Row ~ page-based 16 MB document 400 KB item

    NoSQL trades query flexibility for predictable, single-lookup performance.

    Think of it like…

    A relational design is a library catalogue that can answer any question with some walking; a NoSQL design is a takeaway menu where every popular meal is already boxed, so it is handed over instantly — but a new dish means repacking the kitchen.

    Real-world example

    The fictional TrailMate hiking app lists its access patterns: get a user profile, list a user's recent hikes, show a hike with its photos, list hikes on a trail. In MongoDB it embeds up to 20 photo summaries inside each hike document and references the user by ID. In DynamoDB, a single table uses PK = USER#42 with SK = HIKE#2026-09-14 so one Query returns a user's hikes in date order.

    How it works¶

    1. Write down every access pattern with its filters, sort order, expected volume and latency target.
    2. Group data that is read together: embed child data that is bounded and owned by one parent; reference data that is shared or unbounded.
    3. Design keys: choose partition keys with many distinct, evenly used values and sort keys that support range queries.
    4. Add secondary indexes (GSIs, MongoDB indexes) for the remaining access patterns, overloading generic key names where useful.
    5. Plan how duplicated data is updated and how documents will be versioned as the schema evolves.

    Who uses it

    Backend and mobile developers on MongoDB, DynamoDB, Firestore or Cassandra, and solution architects designing serverless systems.

    Key takeaway

    If asked "how do you design a DynamoDB table?", start with "list the access patterns first" — it is the single most important point.

    Going deeper

    • MongoDB documents are limited to 16 MB and DynamoDB items to 400 KB, so unbounded arrays (every comment ever) must be referenced or bucketed rather than embedded.
    • A DynamoDB partition supports roughly 3,000 read units and 1,000 write units per second, so a key such as the current date that concentrates traffic creates a hot partition and throttling.
    • DynamoDB allows up to 20 global secondary indexes per table by default (eventually consistent, any key) and up to 5 local secondary indexes (same partition key, defined at table creation).
    • Single-table design was popularised by Rick Houlihan's AWS re:Invent talks and Alex DeBrie's The DynamoDB Book (2020); AWS guidance also notes that separate tables are fine when entities are never fetched together.
    • Cassandra modelling is query-first too: one table per query, partition keys sized to stay well under about 100 MB, and clustering columns that define on-disk sort order; Chebotko diagrams document this design.
    • MongoDB's published schema design patterns — bucket, extended reference, subset, computed, outlier, attribute, polymorphic and schema versioning — are reusable answers to recurring document-modelling problems.

    Common mistakes & misconceptions

    • Porting a normalised schema table-for-table into MongoDB or DynamoDB: you lose joins and gain nothing; redesign around access patterns.
    • Embedding unbounded lists: documents grow until they hit size limits and every update rewrites a huge document.
    • Choosing a low-cardinality partition key such as country or status: a few partitions take all the traffic and throttle.

    Apache Cassandra practice · Pattern · Current · Advanced · Wide-column    		 Creating one denormalised table per query, with partition and clustering keys matching that query exactly. hikes_by_trail and hikes_by_user hold the same data, each partitioned for its own query.
    Hot partition
    Distributed NoSQL databases · Concept · Current · Intermediate · General    		 A partition key value receiving far more traffic than others, overloading one storage node and causing throttling. Using PK = DATE#2026-10-08 puts every write for today on one partition; adding a random suffix spreads it.
    Document and item size limits
    MongoDB, DynamoDB, Firestore documentation · Concept · Current · Intermediate · General    		 Hard caps per stored unit — 16 MB MongoDB document, 400 KB DynamoDB item, about 1 MiB Firestore document. A chat app storing all messages in one conversation document hits MongoDB's 16 MB limit after months.

    3.12 Schema Evolution and Migrations¶

    A database schema keeps changing as an application grows: new tables, new columns, renamed fields. A migration is a small, versioned script that makes one change, stored in Git next to the code. Migration tools record which scripts have run in each environment, so development, test and production databases all reach the same version in the same order.

    Think of it like…

    Migrations are like numbered renovation instructions for a house: every builder follows step 1, then 2, then 3, and a logbook on the wall shows which steps this house has already had.

    Real-world example

    The fictional PayDay payroll startup needs to split full_name into first_name and last_name on a 30-million-row table without downtime. It ships an expand migration adding nullable columns, deploys code that writes both, backfills in 10,000-row batches overnight, switches reads to the new columns, and a week later runs a contract migration that drops full_name. Flyway records each step in flyway_schema_history.

    How it works¶

    1. Write each change as a new, numbered migration file; never edit one that has already run in a shared environment.
    2. Review migrations like code and run them automatically in CI against a fresh database.
    3. Apply them in order with a migration tool, which records the version, checksum and time in a history table.
    4. For large or busy tables, use expand-and-contract and online schema change tools to avoid long locks.
    5. Roll forward with a new corrective migration rather than relying on untested down scripts in production.

    Who uses it

    Backend developers, DevOps and platform engineers, DBAs and anyone deploying an application backed by a database.

    Key takeaway

    Know the expand-and-contract (parallel change) pattern and that in PostgreSQL you should use CREATE INDEX CONCURRENTLY and a lock_timeout on busy tables.

    Going deeper

    • In PostgreSQL most ALTER TABLE forms take an ACCESS EXCLUSIVE lock; even a fast change can queue behind a long query and block all traffic, so set lock_timeout (for example 3s) and retry.
    • PostgreSQL 11+ adds a column with a constant default without rewriting the table, and NOT NULL can be added safely via a CHECK ... NOT VALID constraint validated later; MySQL 8.0 supports ALGORITHM=INSTANT for many column additions.
    • Flyway stores applied versions and checksums in flyway_schema_history, Liquibase uses DATABASECHANGELOG plus a DATABASECHANGELOGLOCK table, and Prisma uses _prisma_migrations, so tools detect edited or missing scripts.
    • Liquibase 5.0 (September 2025) moved its Community edition from Apache 2.0 to the source-available Functional Source License, with each release reverting to Apache 2.0 after two years; Flyway Community remains open source under Redgate.
    • Declarative tools such as Atlas compare a desired schema with the live database and generate the migration plan, while imperative tools such as Flyway run the scripts you write.
    • MySQL online schema change tools copy the table in the background — gh-ost by reading the binary log, pt-online-schema-change with triggers — then swap it in with a brief lock.

    Common mistakes & misconceptions

    • Editing an already-applied migration: checksums break and environments silently diverge; always add a new migration instead.
    • Renaming or dropping a column in one step: running application instances still use the old name and start failing mid-deploy.
    • Backfilling millions of rows in one transaction: it locks rows, bloats the WAL and replication lag; batch it in small chunks.

    3.13 Naming Conventions and Design Anti-Patterns¶

    Consistent names make a schema readable for years, and some designs that look clever early on become painful later. Anti-patterns such as Entity-Attribute-Value tables, polymorphic foreign keys or comma-separated lists stop the database from enforcing rules and make queries slow and complex. Each has a well-known better alternative.

    Common anti-patterns and their fixes

    Why it hurts Better design
    Entity-Attribute-Value No types, no constraints, many self-joins Typed columns, plus JSONB for rare extras
    Polymorphic association No real foreign key possible Exclusive arc or shared supertype table
    Comma-separated list Cannot index, join or validate Junction table
    tag1, tag2, tag3 columns Fixed limit, OR-heavy queries Child table, one row per tag
    One true lookup table No FK per code type One lookup table per domain
    FLOAT for money Rounding errors NUMERIC or integer pence
    Table per year Unions and duplicated DDL One table, partitioned by date

    Each fix lets the database enforce types, keys and constraints again.

    Think of it like…

    A schema is a shared kitchen: if everyone labels jars the same way and keeps one ingredient per jar, anyone can cook; if jars are labelled "misc" and hold three spices mixed together, every recipe becomes a puzzle.

    Real-world example

    The fictional CraftBase marketplace stored product details in an EAV table: (product_id, attribute, value) with everything as text. Finding red cotton shirts under £20 needed four self-joins and casts, taking 9 seconds. Moving common attributes into typed columns and rare ones into a JSONB column with a GIN index cut it to 40 ms, and CHECK constraints now stop prices like 'twenty'.

    How it works¶

    1. Agree a naming standard: lowercase snake_case, consistent singular or plural tables, id or table_id keys, and readable constraint names.
    2. Avoid reserved words and quoted mixed-case identifiers so names work in every tool and dialect.
    3. Review designs against known anti-patterns: EAV, polymorphic associations, delimited lists, repeated columns, one-true-lookup tables.
    4. Replace them with typed columns, proper junction tables, exclusive-arc foreign keys or JSONB with validation.
    5. Enforce standards with linters and code review, and record conventions in the repository.

    Who uses it

    Backend developers, DBAs and data modellers doing design reviews; these patterns come up constantly in code reviews and interviews.

    Key takeaway

    Bill Karwin's SQL Antipatterns is the classic reference; for interviews, be able to explain why EAV and polymorphic associations break foreign keys and type checking.

    Going deeper

    • Bill Karwin's SQL Antipatterns (Pragmatic Bookshelf, 2010; revised as Volume 1 in 2022) names many of these, including Jaywalking (delimited lists), Multicolumn Attributes, Metadata Tribbles and Polymorphic Associations.
    • Unquoted identifiers fold to lower case in PostgreSQL and to upper case in Oracle, so a table created as "OrderItems" in quotes must be quoted forever; lowercase snake_case avoids this entirely.
    • Trees in SQL have four classic designs: adjacency list (parent_id, queried with recursive CTEs), path enumeration (PostgreSQL ltree), nested sets (fast reads, slow writes) and closure tables (all ancestor-descendant pairs).
    • Soft deletes (deleted_at columns) keep data recoverable but every query, unique constraint and foreign key must account for them; partial unique indexes such as UNIQUE (email) WHERE deleted_at IS NULL help.
    • Multi-tenant SaaS schemas choose between a shared schema with tenant_id on every row (often with row-level security), a schema per tenant, or a database per tenant, trading cost against isolation.

    Common mistakes & misconceptions

    • Choosing EAV for "flexibility": you lose types, constraints and performance; JSONB plus a few typed columns is usually the better flexible design.
    • Mixing naming styles across tables: CustomerID, customer_id and custId in one schema guarantees bugs in joins and ORMs.
    • Assuming a soft-delete flag is free: forgotten WHERE deleted_at IS NULL filters leak deleted data into reports and APIs.

    Try it: Replace a polymorphic association with an exclusive arc (PostgreSQL)¶

    CREATE TABLE comment (
  comment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  photo_id   bigint REFERENCES photo,
  article_id bigint REFERENCES article,
  body       text NOT NULL,
  -- exactly one parent must be set
  CONSTRAINT comment_one_parent_ck CHECK (num_nonnulls(photo_id, article_id) = 1)
);

    Common SQL convention · Concept · Current · Beginner · Relational    		 Lowercase words joined by underscores for tables and columns, avoiding quoting and case-folding problems across databases. order_line.unit_price works unquoted in PostgreSQL, MySQL, SQL Server and Oracle.

    Anti-pattern (Karwin, SQL Antipatterns) · Pattern · Legacy · Intermediate · Relational    		 Storing data as (entity, attribute name, value) rows, losing types, constraints and simple queries. Finding products where colour = red AND size = M needs two self-joins on product_attribute.
    Polymorphic association

    Anti-pattern (Karwin, SQL Antipatterns) · Pattern · Current · Beginner · Relational    		 Numbered columns like phone1, phone2, phone3 for a repeating attribute, with a fixed limit and awkward queries. Searching any phone number needs WHERE phone1 = ? OR phone2 = ? OR phone3 = ?.
    One true lookup table (OTLT)
    Anti-pattern · Pattern · Current · Intermediate · Relational    		 A single generic table holding every code type, so foreign keys cannot restrict a column to the right kind of code. order.status can accidentally reference a 'country' code because both live in lookup_code.
    Metadata tribbles (table per period)
    Anti-pattern (Karwin, SQL Antipatterns) · Pattern · Current · Intermediate · Relational    		 Splitting one entity into many tables by year, customer or region, multiplying DDL and unions. sales_2024, sales_2025, sales_2026 should be one sales table partitioned by sale_date.
    FLOAT for money
    Anti-pattern · Pattern · Current · Beginner · Relational    		 Using binary floating point for currency, which cannot represent most decimal fractions exactly. 0.1 + 0.2 in a FLOAT column gives 0.30000000000000004; NUMERIC(12,2) gives exactly 0.30.
    Closure table
    Relational tree modelling · Pattern · Current · Advanced · Relational    		 Storing every ancestor-descendant pair of a hierarchy in a separate table for fast subtree queries. A category tree of 5,000 nodes gets category_path(ancestor, descendant, depth) to list all subcategories instantly.
    Soft delete
    Application design pattern · Pattern · Current · Intermediate · Relational    		 Marking rows as deleted with a flag or timestamp instead of removing them, keeping data recoverable. Users with deleted_at set disappear from the app but can be restored within 30 days.
    Multi-tenant schema patterns
    SaaS architecture · Pattern · Current · Intermediate · Relational    		 Shared tables with tenant_id, schema per tenant, or database per tenant — trading cost, isolation and operational effort. A SaaS with 8,000 small customers uses tenant_id plus row-level security; its biggest client gets a dedicated database.
    SQL Antipatterns (book)
    Bill Karwin, Pragmatic Bookshelf · Resource · Current · Intermediate · Relational    		 Classic book cataloguing common SQL design and query mistakes, each with the recommended solution. A team uses its chapters as a checklist during schema design reviews.

    3.14 Choosing Data Types Well¶

    Every column has a data type that decides what values it can hold, how much space it takes and how it sorts and compares. Good choices catch bad data early, save storage and keep calculations correct. Poor choices — text for dates, floats for money, 32-bit integers for fast-growing IDs — cause subtle bugs that are expensive to fix later.

    Think of it like…

    Data types are like containers in a kitchen: an egg box for eggs, a measuring jug for liquid; putting soup in an egg box technically works for a moment, then makes a mess.

    Real-world example

    The fictional FlyEasy travel site stored booking times as text like '03/04/2026 14:00'. Half the rows were US-format, half UK, and sorting was alphabetical. Converting to timestamptz (stored in UTC) fixed sorting and time-zone display; prices moved from float to numeric(10,2), ending a £0.01 mismatch in daily revenue reports.

    How it works¶

    1. Pick the most specific type that fits the meaning: date for dates, boolean for yes/no, numeric for money.
    2. Size integer columns for growth: bigint for IDs and counters on anything that might pass 2 billion rows.
    3. Store moments in time as timestamp with time zone (UTC), and use date when time of day does not matter.
    4. Use text with CHECK constraints or lookup tables rather than oversized varchar limits or fragile enums.
    5. Choose the right character set and collation (UTF-8, case and accent rules) before loading data.

    Who uses it

    Everyone who writes CREATE TABLE: backend developers, DBAs, data engineers and analysts loading data into warehouses.

    Key takeaway

    Interview favourites: never use float for money, use timestamptz for events, use bigint for IDs, and in MySQL use utf8mb4 rather than utf8.

    Going deeper

    • PostgreSQL's timestamptz stores an 8-byte UTC instant and converts to the session's TimeZone for display; plain timestamp stores wall-clock time with no zone, which is ambiguous across daylight-saving changes.
    • MySQL's TIMESTAMP is a 32-bit Unix time ending 2038-01-19 03:14:07 UTC (the Year 2038 problem), while DATETIME reaches 9999-12-31; MySQL's utf8 alias means 3-byte utf8mb3, which cannot store emoji — use utf8mb4, the default since 8.0.
    • IEEE 754 doubles hold about 15-17 significant decimal digits but cannot represent 0.1 exactly; NUMERIC/DECIMAL stores exact decimal digits, and many payment systems store integer minor units (pence, cents).
    • In PostgreSQL varchar(n) and text perform the same; the limit is only a constraint. SQL Server distinguishes varchar from Unicode nvarchar (UTF-16) and has supported UTF-8 collations since SQL Server 2019.
    • Column order affects row size through alignment padding: PostgreSQL aligns 8-byte types on 8-byte boundaries, so placing bigint and timestamptz columns before smaller ones can save several bytes per row.
    • SQLite uses flexible type affinity and accepts almost any value in any column unless you declare a STRICT table (available since 3.37.0, 2021); Oracle Database 23ai finally added a native SQL BOOLEAN type.

    Common mistakes & misconceptions

    • Storing dates as text: sorting, range filters and validation all break; use date or timestamptz and format only for display.
    • Using 32-bit int for IDs on growing tables: hitting 2,147,483,647 forces an emergency column rewrite under pressure.
    • Using timestamp without time zone for events from many regions: daylight-saving shifts and offsets corrupt ordering and reports.

    Try it: See type behaviour and sizes in PostgreSQL¶

    SELECT 0.1::float8 + 0.2::float8           AS float_sum,    -- 0.30000000000000004
       0.1::numeric + 0.2::numeric         AS numeric_sum,  -- 0.3

    SQL standard · Concept · Current · Beginner · Relational    		 True/false (and NULL) values; supported natively in PostgreSQL and MySQL (as TINYINT(1)), and in Oracle since 23ai. is_active boolean NOT NULL DEFAULT true is clearer than a char(1) holding 'Y' or 'N'.

    INTERVAL
    SQL standard · Concept · Current · Intermediate · Relational    		 A span of time such as 3 days or 2 hours 15 minutes, usable in date arithmetic. WHERE created_at > now() - interval '7 days' finds last week's sign-ups.

    SQL:2016 JSON; PostgreSQL, MySQL · Concept · Current · Intermediate · Relational    		 Types for semi-structured data; PostgreSQL's JSONB stores a parsed binary form that can be indexed with GIN. A product's optional specs live in a JSONB column queried with specs @> '{"material":"cotton"}'.
