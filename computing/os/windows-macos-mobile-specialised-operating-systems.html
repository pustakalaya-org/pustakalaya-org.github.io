    Chapter 5: Windows, macOS, Mobile & Specialised Operating Systems¶

    Linux is only one corner of the operating-system world. This chapter opens up Windows — the NT architecture, boot and registry internals, the 2026 versions and servicing model, Windows Server 2025, PowerShell and WSL — then macOS, iOS and iPadOS, Android and AOSP, ChromeOS and HarmonyOS, the BSD family and the real-time and embedded systems hidden inside cars and medical devices. It ends with the security mechanisms all modern operating systems share, from ASLR and stack canaries to SELinux, sandboxing and Secure Boot.

    5.1 Windows Architecture: The NT Kernel and Its Layers¶

    Every modern Windows — Windows 11, Windows Server, even Xbox — is built on the Windows NT design first shipped in 1993. Programs never touch the hardware: they call documented Windows functions (the Win32 API), which pass the request through a thin library called ntdll.dll into kernel mode, where the NT executive, the kernel, device drivers and the Hardware Abstraction Layer (HAL) do the real work.

    Think of it like…

    Windows is like a big hotel: guests (apps) only ever talk to the front desk (the Win32 API); behind the 'staff only' door, specialist departments (the executive's managers) handle rooms, keys and luggage, and the building's foundations (the HAL) let the same hotel design stand on different ground.

    Real-world example

    Amara, a support engineer at the fictional Kestrel Logistics, traces what happens when a warehouse app saves a delivery note. The app calls WriteFile in kernelbase.dll, which calls NtWriteFile in ntdll.dll and switches the CPU into kernel mode. The I/O manager wraps the request in an I/O Request Packet and passes it down through an antivirus filter, the NTFS driver and the storage driver to the SSD, and the success code travels back up the same path.

    How it works¶

    1. An application calls a documented Win32 function such as CreateFileW, implemented in kernelbase.dll (kernel32.dll forwards to it).
    2. kernelbase.dll calls the matching native API stub (NtCreateFile) in ntdll.dll, which loads a system service number and executes the CPU's syscall instruction.
    3. In kernel mode the system service dispatcher runs the executive routine; the Object Manager creates the object and a handle, and the Security Reference Monitor checks its access control list.
    4. For I/O, the I/O manager builds an I/O Request Packet (IRP) and sends it down a stack of drivers: filters, file system, volume and storage port drivers.
    5. The kernel schedules threads and handles interrupts, while hal.dll hides chipset and interrupt-controller differences.
    6. An NTSTATUS result returns up the stack and is translated into a Win32 error code for the application.

    Who uses it

    Windows administrators, desktop and server support staff, driver developers, security analysts, incident responders and malware reverse engineers all rely on this model.

    Key takeaway

    Memorise the call path for interviews: Win32 DLLs → ntdll.dll (native API) → syscall → ntoskrnl.exe (executive + kernel) → drivers → HAL — and call Windows a hybrid kernel.

    Going deeper

    • Windows NT was designed by a team led by Dave Cutler, formerly of DEC's VMS group; NT 3.1 shipped in July 1993 and every current Windows client and server release descends from it.
    • ntoskrnl.exe holds both the executive (Object Manager, Memory Manager, I/O Manager, Process Manager, Security Reference Monitor, Configuration Manager) and the low-level kernel that schedules threads and dispatches interrupts.
    • Windows is usually called a hybrid kernel: it keeps a layered, object-based design inspired by microkernels, but runs nearly all services, drivers and the win32k graphics component in kernel mode for speed.
    • System service numbers used by ntdll.dll stubs change between builds, which is one reason Microsoft only supports the documented Win32 API; tools like Sysinternals and EDR products inspect this boundary.
    • Interrupt Request Levels order work: PASSIVE_LEVEL 0, APC_LEVEL 1, DISPATCH_LEVEL 2, then device levels; touching pageable memory at DISPATCH_LEVEL or above produces the classic IRQL_NOT_LESS_OR_EQUAL stop error.
    • On 64-bit Windows, Kernel Patch Protection (PatchGuard) periodically checks critical kernel structures, and since Windows 10 version 1607 new kernel drivers must be signed through Microsoft's Hardware Dev Center portal.
    • Windows on Arm runs native ARM64 code, emulates x86 and x64 apps with the Prism emulator, and offers ARM64EC so developers can port an app gradually while mixing native and emulated code in one process.

    Common mistakes & misconceptions

    • 'Win32 means 32-bit' — Win32 is simply the API name; 64-bit Windows still calls it Win32, and its 64-bit system DLLs confusingly live in System32.
    • Calling Windows a microkernel — most operating-system services and all drivers run in kernel mode, so a faulty driver can still crash the whole machine.
    • Calling undocumented Nt* functions in production code — their numbers and behaviour can change in any update; use documented Win32 or .NET APIs.

    Try it: See which Windows build you run and the core DLLs loaded in your PowerShell process¶

    # PowerShell (no admin needed)
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber, OSArchitecture
(Get-Process -Id $PID).Modules | Where-Object ModuleName -in 'ntdll.dll','kernel32.dll','KERNELBASE.dll' | Select-Object ModuleName, FileName
driverquery | Select-Object -First 15

    Microsoft · Concept · Current · Advanced    		 64-bit Windows loads only Microsoft-signed kernel drivers and blocks known-vulnerable signed drivers abused by attackers. Ransomware tries a 'bring your own vulnerable driver' attack, but the blocklist stops the old driver from loading.
    I/O Request Packet (IRP)
    Microsoft I/O Manager · Concept · Current · Advanced    		 The data structure describing one I/O operation, passed down a stack of layered drivers and completed back up. An antivirus file-system minifilter sees the IRP for a file open and scans the file before NTFS completes it.
    IRQL (Interrupt Request Level)
    Microsoft kernel · Concept · Current · Advanced    		 A per-CPU priority level deciding which interrupts may preempt running code and whether page faults are allowed. A buggy network driver touches paged memory at DISPATCH_LEVEL and the PC stops with IRQL_NOT_LESS_OR_EQUAL.
    Handles and the Object Manager namespace
    Microsoft · Concept · Current · Intermediate    		 Kernel resources are objects in a namespace; processes get per-process handles referring to them, never raw pointers. Sysinternals Handle.exe reveals which process holds a lock on report.xlsx so the admin can close it.
    WoW64
    Microsoft · Component · Current · Intermediate    		 'Windows 32-bit on Windows 64-bit': a user-mode layer that runs 32-bit x86 programs on 64-bit Windows. A 32-bit legacy accounting app installs to Program Files (x86) and has its registry writes redirected to WOW6432Node.
    Prism emulator
    Microsoft (Windows 11 24H2+) · Component · Current · Intermediate    		 Windows on Arm's translator that runs x86 and x64 apps on Arm CPUs such as Snapdragon X, caching translated code. A Snapdragon X laptop runs an older x64-only VPN client through Prism while Office runs natively as ARM64.
    ARM64EC
    Microsoft · API · Current · Advanced    		 An application binary interface letting native Arm code and emulated x64 code mix inside one process during porting. A CAD vendor recompiles its core engine as ARM64EC while still loading an old x64-only plug-in.
    Kernel Patch Protection (PatchGuard)
    Microsoft · Component · Current · Advanced    		 A 64-bit Windows feature that detects modification of critical kernel structures and deliberately crashes the system. Security vendors had to move from kernel hooking to official callbacks and minifilters after PatchGuard arrived in x64 Windows.

    5.2 Windows Internals: Boot, Core Processes, Registry and Services¶

    When a Windows PC starts, firmware hands over to the Windows Boot Manager, which loads the kernel; the kernel then starts a small chain of trusted system processes that launch services and the logon screen. Settings for the whole system live in the registry, a hierarchical database, and background programs called services run without anyone logged in.

    Think of it like…

    Booting Windows is like opening a theatre: the caretaker unlocks the building (firmware), the stage manager reads the running order (boot configuration), the crew sets up (kernel and drivers), the ushers take their places (services) and finally the doors open to the audience (the logon screen). The registry is the production's master notebook.

    Real-world example

    At the fictional Fernbrook College, lab PCs suddenly take four minutes to reach the logon screen. Technician Dev opens Event Viewer and sees a service timing out, uses Autoruns to find a forgotten licence-server service set to Automatic start, and changes it to Automatic (Delayed Start) with sc.exe. Boot time drops to 35 seconds.

    How it works¶

    1. UEFI firmware verifies and runs bootmgfw.efi (Windows Boot Manager), which reads the Boot Configuration Data (BCD) store.
    2. winload.efi loads ntoskrnl.exe, hal.dll, the SYSTEM registry hive and boot-start drivers, then transfers control to the kernel.
    3. The kernel initialises and starts smss.exe (Session Manager), which starts csrss.exe and wininit.exe for session 0.
    4. wininit.exe starts services.exe (the Service Control Manager) and lsass.exe (authentication); services start according to their start type.
    5. smss.exe creates the user session, where winlogon.exe shows LogonUI; after sign-in userinit.exe launches explorer.exe.

    Who uses it

    Desktop support technicians, Windows and Active Directory administrators, digital forensics investigators and SOC analysts work with boot, registry and service internals every day.

    Key takeaway

    Know the normal parent-child chain (wininit → services → svchost; wininit → lsass) — a second lsass.exe or a svchost.exe outside System32 is a classic malware red flag.

    Going deeper

    • The registry is stored in hive files under C:\Windows\System32\config (SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT) plus each user's NTUSER.DAT and UsrClass.dat; HKEY_LOCAL_MACHINE and HKEY_USERS are the only real root keys.
    • Service start types are Boot (0), System (1), Automatic (2), Manual (3) and Disabled (4), stored as the Start value under HKLM\SYSTEM\CurrentControlSet\Services\<name>.
    • Since Windows 10 version 1703, machines with more than about 3.5 GB of RAM run most services in their own svchost.exe instance, which makes troubleshooting and crash isolation easier.
    • Fast Startup hibernates the kernel session at shutdown, so 'Shut down' is not a full restart; use Restart when drivers or updates need a clean boot.
    • The Windows Recovery Environment (WinRE) lives on a small recovery partition and offers Startup Repair, System Restore, Safe Mode and a command prompt with bcdedit and bootrec.
    • Persistence locations attackers love include Run/RunOnce registry keys, services, scheduled tasks and WMI subscriptions; Sysinternals Autoruns lists them all in one view.
    • User Account Control (UAC), introduced with Windows Vista in 2007, gives admins a filtered standard-user token and asks for consent before using the full administrator token.

    Common mistakes & misconceptions

    • Editing the registry without a backup — export the key first (reg export) or create a restore point; a bad change to SYSTEM can stop Windows booting.
    • Assuming every svchost.exe is suspicious — dozens are normal; check the path (System32), parent (services.exe) and command line instead.
    • Treating UAC as a security boundary — Microsoft does not; elevated malware and UAC bypasses exist, so run daily work as a standard user.

    Try it: Inspect services, a registry value and the boot entry (bcdedit needs an admin prompt)¶

    Get-Service | Where-Object Status -eq 'Running' | Select-Object -First 10 Name, StartType
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' | Select-Object ProductName, DisplayVersion, CurrentBuild
Get-CimInstance Win32_Process -Filter "Name='lsass.exe'" | Select-Object ProcessId, ParentProcessId, ExecutablePath
bcdedit /enum '{current}'   # admin only

    Microsoft · Component · Current · Intermediate    		 Handles interactive sign-in, the secure attention sequence (Ctrl+Alt+Del), lock screen and sign-out. Windows Hello for Business is a credential provider shown by LogonUI alongside password and smart-card options.

    Windows services
    Microsoft · Concept · Current · Beginner    		 Background programs managed by the SCM, running under accounts like LocalSystem, NetworkService or a managed service account. A backup agent runs as a service so nightly jobs work even when nobody is signed in.
    Event Viewer and Windows Event Log
    Microsoft (eventvwr.msc, wevtutil) · Tool · Current · Beginner    		 Records system, application and security events; each event has a source, ID, level and timestamp. Security event 4625 records failed logons; a burst of them from one IP suggests a password-spraying attempt.

    Microsoft (taskschd.msc, schtasks) · Tool · Current · Beginner    		 Runs programs at set times or on triggers like logon, idle or a specific event log entry. schtasks /create /sc daily /st 02:00 /tn Cleanup /tr C:\Scripts\cleanup.cmd schedules a nightly script.

    Microsoft (Windows Vista, 2007) · Component · Current · Beginner    		 Runs admins with a filtered token and asks for consent before elevating a process to full administrator rights. Installing a printer driver triggers a UAC prompt even for an administrator account.
    Windows Recovery Environment (WinRE)
    Microsoft · Platform · Current · Intermediate    		 A small recovery OS used for Startup Repair, Safe Mode, System Restore, reset and a recovery command prompt. After a failed driver update, a technician boots WinRE, opens Safe Mode and rolls the driver back.
    Sysinternals Autoruns
    Microsoft Sysinternals (Mark Russinovich) · Tool · Current · Intermediate    		 Shows every auto-start location — Run keys, services, drivers, scheduled tasks, shell extensions — in one list. An analyst hides signed Microsoft entries in Autoruns and spots an unsigned service pointing into AppData.

    5.3 Windows 11 and 10 in 2026: Versions, Servicing and End of Support¶

    Windows 11 gets one feature update a year, named after the half-year it ships (24H2, 25H2, 26H2), plus security updates every month. Windows 10 reached end of support on 14 October 2025, so only devices enrolled in paid or free Extended Security Updates (ESU) still receive patches.

    Think of it like…

    Windows versions are like car model years: the 2025 model looks almost the same as the 2026 model, the garage sends monthly safety recalls, and after a set number of years the manufacturer stops servicing that model unless you buy an extended warranty.

    Real-world example

    Mina manages 600 PCs at the fictional Larkspur Housing Association. In 2025 she replaced 120 PCs that failed Windows 11's TPM 2.0 and CPU checks, enrolled 40 kiosks in commercial ESU at $61 each for year one, and moved everyone else from 23H2 to 24H2 and then 25H2 through a simple enablement package.

    How it works¶

    1. Microsoft develops the next release in Windows Insider channels (Canary, Dev, Beta, Release Preview).
    2. Security and quality fixes ship as cumulative updates on Patch Tuesday, the second Tuesday of each month.
    3. One feature update ships each autumn; recent ones (25H2, 26H2) are small enablement packages that switch on features already delivered.
    4. Home and Pro editions are supported for 24 months per version; Enterprise and Education for 36 months.
    5. When support ends the device must move to a newer version, a Long-Term Servicing Channel (LTSC) edition, or ESU.

    Who uses it

    Desktop engineers, endpoint and Intune administrators, IT asset managers, help-desk staff and security teams track versions, update rings and end-of-support dates.

    Key takeaway

    Remember three dates: Windows 10 support ended 14 October 2025; Windows 11 24H2 Home/Pro updates end 13 October 2026; feature updates ship once a year in the second half.

    Going deeper

    • Windows 11 minimum hardware: 64-bit CPU with 2+ cores at 1 GHz from the supported list (roughly Intel 8th gen / AMD Ryzen 2000 or newer), 4 GB RAM, 64 GB storage, UEFI with Secure Boot capability and TPM 2.0.
    • Windows 10 commercial ESU costs $61 per device for year one and doubles each year for up to three years (to October 2028); Windows 365 and Azure Virtual Desktop VMs get ESU at no extra cost.
    • Consumer ESU could be obtained free by syncing settings with Windows Backup, with 1,000 Microsoft Rewards points, or for about $30; in mid-2026 Microsoft's documentation extended consumer coverage to 12 October 2027.
    • Windows 11 Enterprise LTSC 2024 (build 26100) gets 5 years of support and IoT Enterprise LTSC 2024 gets 10 years, with no feature updates — intended for kiosks, ATMs and medical devices, not office PCs.
    • Hotpatch for Windows 11 Enterprise 24H2 and later installs most monthly security fixes without a restart; only quarterly baseline months (January, April, July, October) need a reboot.
    • Windows 11 26H1 is a special platform release for new Snapdragon X2 devices only; those PCs cannot move to 26H2, while Intel, AMD and older Arm PCs follow the normal 24H2 → 25H2 → 26H2 path.
    • Copilot+ PCs need an NPU of at least 40 TOPS, 16 GB RAM and 256 GB storage, and unlock on-device AI features such as Recall, which is opt-in and protected with Windows Hello and VBS enclaves.

    Common mistakes & misconceptions

    • Thinking Windows 10 PCs stop working after October 2025 — they still run, but without security fixes they become steadily riskier to use online.
    • Bypassing the Windows 11 hardware check on unsupported PCs in a business — Microsoft does not guarantee updates there, and it may break compliance.
    • Confusing the build number with the version: 25H2 is build 26200 and 24H2 is 26100; check both plus the UBR (monthly patch level).

    Try it: Check your exact Windows version and build¶

    winver
# or in PowerShell:
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion' | Select-Object DisplayVersion, CurrentBuild, UBR
Get-ComputerInfo -Property OsName, OsVersion, WindowsVersion

    5.5 PowerShell and Windows Admin Tools¶

    PowerShell is Microsoft's command-line shell and scripting language. Unlike classic shells that pass text between commands, PowerShell passes structured .NET objects, so you can sort, filter and export real properties without parsing text. Around it sit admin tools such as winget, Sysinternals, Event Viewer, Group Policy and Intune.

    Think of it like…

    A text shell is like passing handwritten notes along a line of people who must re-read each note; PowerShell is like passing labelled boxes — each person can open exactly the compartment they need.

    Real-world example

    Jonas, a junior admin at the fictional Brightwater Clinic, must find PCs whose disks are over 90% full. He writes a 6-line PowerShell script that queries 80 PCs over PowerShell remoting, filters objects where free space is under 10%, and exports a CSV for his manager — a job that would take a day by hand.

    How it works¶

    1. Commands are cmdlets named Verb-Noun, such as Get-Service or Stop-Process; Get-Command and Get-Help find and explain them.
    2. Each cmdlet outputs objects; Get-Member shows their properties and methods.
    3. The pipeline (|) hands whole objects to the next command, e.g. Where-Object to filter and Sort-Object to order them.
    4. Format-Table, Export-Csv or ConvertTo-Json present or save the results at the end of the pipeline.
    5. Invoke-Command and Enter-PSSession run the same commands on remote machines over WinRM or SSH.

    Who uses it

    Windows and Microsoft 365 administrators, cloud engineers (Azure and Microsoft Graph), DevOps engineers, help-desk staff and blue-team security analysts use PowerShell daily.

    Key takeaway

    Know that Windows PowerShell 5.1 (built in, .NET Framework) is in maintenance mode, while PowerShell 7 (pwsh, cross-platform) is current — 7.6 LTS, released March 2026, runs on .NET 10.

    Going deeper

    • PowerShell 1.0 shipped in 2006; Windows PowerShell 5.1 (2016) is the last .NET Framework version and still ships with Windows, while open-source PowerShell 7 runs on Windows, Linux and macOS.
    • PowerShell 7.4 LTS (on .NET 8) is supported until November 2026; PowerShell 7.6 LTS reached general availability in March 2026 on .NET 10 and is the recommended production version.
    • Execution policy (Restricted, RemoteSigned, AllSigned, Bypass) prevents accidental script runs but Microsoft states it is not a security boundary; use AppLocker or App Control for Business to block scripts.
    • Script block logging (Event ID 4104 in Microsoft-Windows-PowerShell/Operational) and transcription record what ran, which is why defenders enable them and attackers try to downgrade to PowerShell 2.0, now removed from current Windows 11.
    • Modules come from the PowerShell Gallery via Install-PSResource (PSResourceGet) or the older Install-Module; Microsoft.Graph and Az modules manage Microsoft 365 and Azure.
    • Desired State Configuration (DSC) describes how a machine should look; DSC v3 is a rewritten cross-platform engine that can be driven from other tools.
    • sudo for Windows (Windows 11 24H2 and later) lets you elevate a single command from a normal terminal after enabling it in Settings, similar to sudo on Linux.

    Common mistakes & misconceptions

    • Parsing PowerShell output as text — use object properties ($_.Name) instead of string splitting; formatted output (Format-Table) is for display only.
    • Using Format-Table before Export-Csv — Format-* cmdlets produce formatting objects, so export first and format last.
    • Setting ExecutionPolicy Bypass machine-wide 'to make scripts work' — sign scripts or use RemoteSigned for your user scope instead.

    5.6 WSL: Running Linux Inside Windows¶

    The Windows Subsystem for Linux (WSL) lets you run real Linux distributions such as Ubuntu or Debian on Windows without dual-booting. WSL 2, the default, runs a genuine Linux kernel inside a small, fast-starting virtual machine that Windows manages for you, so Linux tools, Docker and GPU-accelerated AI frameworks work almost as on a Linux PC.

    WSL 1 vs WSL 2

    WSL 1 (2016) WSL 2 (2019+)
    How Linux runs syscalls translated to NT real Linux kernel in a utility VM
    Syscall compatibility partial full
    Docker / containers not supported supported (Docker Desktop backend)
    Linux-side file I/O slower near native ext4 speed
    Access to Windows files fast slower (via 9P)
    Networking shares host stack NAT or mirrored mode
    GPU / GUI apps no CUDA, DirectML, WSLg

    WSL 2 trades a little start-up cost for full Linux compatibility and fast Linux-side file I/O.

    Think of it like…

    WSL 2 is like a self-contained studio flat built inside your house: it has its own kitchen and plumbing (a real Linux kernel), but shares your front door, internet connection and some cupboards (files and networking) with the main house.

    Real-world example

    Leila, a data-science student at the fictional Northgate University, has a Windows laptop with an NVIDIA GPU. She runs wsl --install, gets Ubuntu, clones her project into her Linux home folder, and trains a PyTorch model using CUDA inside WSL. VS Code on Windows edits the files through its WSL extension, and her lab's Linux scripts run unchanged.

    How it works¶

    1. wsl --install enables the Virtual Machine Platform feature, installs WSL from the Microsoft Store and downloads Ubuntu by default.
    2. Windows starts a lightweight utility VM on Hyper-V technology running Microsoft's Linux kernel build.
    3. Each distribution runs as an isolated container-like environment inside that single VM, sharing its kernel.
    4. Windows files appear inside Linux under /mnt/c, and Linux files appear in Explorer under \\wsl.localhost\<distro>.
    5. WSLg adds Linux GUI apps through a Wayland/X server and RDP, and GPU paravirtualisation exposes the Windows GPU driver to Linux.

    Who uses it

    Software developers, data scientists, DevOps engineers, students learning Linux on a Windows laptop and security testers use WSL every day.

    Key takeaway

    Keep project files inside the Linux file system (~/project), not under /mnt/c — cross-OS file access goes through a network-style protocol and can be many times slower for builds.

    Going deeper

    • WSL 1 shipped in the Windows 10 Anniversary Update (2016) using 'pico processes' and kernel drivers (lxss/lxcore) that translate Linux system calls into NT calls; it is still available with wsl --set-version <distro> 1.
    • WSL 2 arrived in Windows 10 version 2004 (2020); its kernel source is published as microsoft/WSL2-Linux-Kernel and Microsoft updates it through wsl --update, moving to newer LTS kernels over time.
    • Since 2022 WSL is delivered and updated through the Microsoft Store, and in May 2025 Microsoft open-sourced most of WSL's code on GitHub (github.com/microsoft/WSL).
    • systemd can run as PID 1 inside a distribution by adding [boot] systemd=true to /etc/wsl.conf; global VM settings such as memory, processors and networkingMode go in %UserProfile%\.wslconfig.
    • Mirrored networking mode (Windows 11 22H2+) gives Linux the same IP addresses as Windows, improving VPN and IPv6 support compared with the default NAT mode.
    • The utility VM grows its memory on demand; settings such as autoMemoryReclaim return cached memory to Windows, and the virtual disk (ext4.vhdx) grows automatically but must be compacted to shrink.
    • Explorer reaches Linux files through the Plan 9 (9P) file server inside WSL, and Linux reaches Windows drives through drvfs — which is why crossing the boundary is slower than staying on one side.

    Common mistakes & misconceptions

    • Storing a Node.js or Python project on /mnt/c and wondering why builds are slow — move it into the Linux home directory.
    • Editing Linux files with Windows tools via the raw ext4.vhdx path — always use \\wsl.localhost paths or VS Code's WSL extension to avoid corruption.
    • Assuming WSL is a security boundary like a separate VM — code in WSL runs as your Windows user and can reach your Windows files.

    5.7 macOS Architecture: XNU, Darwin, launchd, APFS and Apple Silicon¶

    macOS is Apple's desktop operating system. Its core, Darwin, is open source and built around the XNU kernel — a blend of the Mach microkernel and FreeBSD code — with launchd as the first process and APFS as the file system. Since 2020 Macs use Apple's own Arm-based chips (Apple silicon), and macOS 27, released in September 2026, runs only on them.

    Think of it like…

    XNU is like a car built from two proven designs: a Mach chassis that handles the basic moving parts (tasks, threads, messages, memory) and a BSD body that gives drivers the familiar Unix controls (processes, files, networking).

    Real-world example

    Theo, a developer at the fictional Saltmarsh Studios, moves from an Intel MacBook Pro to an M4 MacBook Air. His Intel-only audio plug-in still opens through Rosetta 2, but macOS 26 warns that Rosetta's general availability is ending, so he asks the vendor for a universal binary. He uses launchctl to check his background sync agent and diskutil to look at APFS snapshots.

    How it works¶

    1. Apple silicon's Boot ROM verifies and starts the low-level boot loader (iBoot), which verifies and loads the kernel.
    2. XNU starts: Mach sets up tasks, threads, virtual memory and ports; the BSD layer provides processes, users, POSIX system calls, sockets and the VFS.
    3. XNU launches launchd as PID 1, which reads property-list job definitions in LaunchDaemons and LaunchAgents folders.
    4. launchd starts system daemons, then loginwindow; after sign-in it starts per-user agents and the Finder and Dock.
    5. Apps built with AppKit or SwiftUI link Apple frameworks, which call libSystem and ultimately XNU system calls or Mach messages.

    Who uses it

    Mac administrators, Apple platform developers, creative-industry IT staff, enterprise device managers and security researchers who analyse macOS malware work at this level.

    Key takeaway

    In interviews say 'XNU = Mach + BSD + I/O Kit', remember launchd is PID 1, and know macOS has been a certified UNIX 03 system since Leopard (10.5).

    Going deeper

    • XNU ('X is Not Unix') came from NeXTSTEP: Mach 3.0-derived code for tasks, threads, IPC ports and virtual memory, a BSD layer derived from FreeBSD, and I/O Kit, an object-oriented driver framework written in a C++ subset.
    • Mac OS X 10.0 shipped in 2001; Apple has used year-based version numbers since macOS 26 Tahoe (September 2025), the last release for Intel Macs; macOS 27 (September 2026) supports Apple silicon only.
    • APFS replaced HFS+ in macOS 10.13 High Sierra (2017): copy-on-write metadata, instant file clones, snapshots, space sharing between volumes in one container, and native encryption.
    • Rosetta 2 translates x86-64 apps to Arm mostly ahead of time when first launched, with a JIT for generated code; Apple has said it remains generally available through macOS 27 and will be limited to older games from macOS 28.
    • Apple silicon chips use unified memory shared by CPU, GPU and Neural Engine, and arm64e binaries use pointer authentication (PAC) to make memory-corruption exploits harder.
    • Kernel extensions (kexts) are deprecated; drivers and security tools now use user-space DriverKit drivers and System Extensions such as the Endpoint Security and Network Extension frameworks.
    • Executables are Mach-O files; universal binaries hold both arm64 and x86_64 code, and system libraries are pre-linked into the dyld shared cache for faster app launch.

    Common mistakes & misconceptions

    • Calling macOS 'BSD' — it uses BSD code and APIs, but the kernel is XNU with a Mach core and Apple's own drivers.
    • Assuming Intel-only apps will run forever via Rosetta 2 — plan for universal or Arm builds before macOS 28.
    • Deleting APFS snapshots to 'free space' blindly — Time Machine local snapshots are purged automatically when space is needed.

    5.8 macOS Security: SIP, Gatekeeper, Notarisation and Privacy Controls¶

    macOS protects itself in layers: the system files are sealed and read-only, apps must be signed and checked by Apple before they run, and apps must ask your permission before using the camera, microphone, files or screen. Even an administrator cannot casually modify the OS because System Integrity Protection blocks it.

    Think of it like…

    macOS security is like an apartment building: the structure is sealed by the builder (SIP and the sealed system volume), a doorman checks everyone's ID badge at the entrance (Gatekeeper and notarisation), and each flat's owner decides which visitors may enter which rooms (privacy permissions).

    Real-world example

    Priya, the Mac admin at the fictional Juniper Design agency, gets a call: a designer cannot open a downloaded font utility. Gatekeeper blocked it because it is unsigned. Priya checks the developer, finds a notarised version on the vendor's site and deploys it through MDM, together with a privacy profile pre-approving the agency's screen-recording tool.

    How it works¶

    1. When a file is downloaded, the browser adds the com.apple.quarantine extended attribute.
    2. On first launch, Gatekeeper checks the Developer ID code signature and the notarisation ticket (stapled or fetched online).
    3. XProtect scans the app with Apple's malware signatures; known-bad software is blocked and can be removed.
    4. The user confirms the first launch; unsigned apps must be allowed manually in System Settings → Privacy & Security.
    5. While running, the app is constrained by TCC privacy permissions, its sandbox (if any) and SIP protections.

    Who uses it

    Mac administrators, endpoint security engineers, Apple platform developers who sign and notarise apps, and macOS threat researchers.

    Key takeaway

    Know the trio: Gatekeeper decides whether an app may run, notarisation is Apple's automated malware scan of a developer's app, and SIP stops even root from modifying protected system locations.

    Going deeper

    • System Integrity Protection (OS X 10.11 El Capitan, 2015) blocks writes to /System, /usr (except /usr/local) and protected processes even for root; it can be changed only from recoveryOS with csrutil.
    • Since macOS 11 Big Sur the system lives on a Signed System Volume: a read-only APFS snapshot whose every file is hashed into a Merkle tree, so any tampering breaks the seal and boot verification.
    • Notarisation became mandatory for Developer ID software in macOS 10.15 Catalina (2019); developers upload builds with notarytool, Apple scans them, and stapler attaches the ticket for offline checks.
    • macOS 15 Sequoia removed the old Control-click 'Open' bypass for unsigned apps; users must now approve them in System Settings → Privacy & Security, which makes social-engineering harder.
    • TCC (Transparency, Consent and Control) stores privacy decisions in TCC.db databases; MDM can pre-approve some permissions through PPPC profiles, but camera and microphone access still need user consent.
    • FileVault 2 encrypts the data volume with XTS-AES-128 using a 256-bit key; on Apple silicon the keys are protected by the Secure Enclave, and recovery keys can be escrowed to MDM.
    • Apple's built-in malware defence has three parts: XProtect signatures (YARA-based), XProtect Remediator scans in the background, and Gatekeeper/notarisation revocation of compromised developer certificates.

    Common mistakes & misconceptions

    • Disabling SIP to install a tool and forgetting to re-enable it — it removes a major protection; prefer tools that work with SIP enabled.
    • Believing Macs do not get malware — infostealers like Atomic Stealer target macOS widely, often via fake installers that trick users into bypassing Gatekeeper.
    • Thinking signing alone means safe — signing proves who built the app; notarisation and XProtect are what scan it for known malware.

    5.9 iOS and iPadOS: Apple's Mobile Operating Systems¶

    iOS runs the iPhone and iPadOS runs the iPad; both share the same Darwin/XNU core as macOS but are far more locked down. Every app must be signed, runs in its own sandbox, and normally comes from the App Store. Apple releases one major version a year — iOS 26 in 2025 and iOS 27 in September 2026.

    Think of it like…

    An iPhone is like a gated community with strict rules: every house (app) is built by approved builders, each family stays in its own house, visitors need the owner's permission, and security guards (the Secure Enclave and secure boot) watch the gates.

    Real-world example

    Nadia, IT lead at the fictional Harbourview Hotels, gives 300 front-desk staff iPhones. They are enrolled through Apple Business Manager and supervised by MDM, so the hotel can push its booking app, enforce a passcode and wipe lost phones. Employee data stays separate from personal apps on staff-owned devices through User Enrollment.

    How it works¶

    1. The Boot ROM, burned into the chip, verifies iBoot, which verifies the kernel — an unbroken chain of trust.
    2. XNU starts launchd, which starts system services and SpringBoard, the home-screen app.
    3. Each app is code-signed, installed into its own sandbox container, and receives only the entitlements Apple granted.
    4. File-level Data Protection encrypts each file with keys tied to the passcode and the Secure Enclave.
    5. Sensitive resources (photos, location, contacts, camera) need explicit user permission through privacy prompts.

    Who uses it

    Mobile developers, enterprise mobility (MDM) administrators, mobile security researchers, app-store reviewers and forensic examiners.

    Key takeaway

    Know that every iOS app is sandboxed and signed, that Data Protection encrypts per file using the passcode plus Secure Enclave keys, and that the EU's Digital Markets Act allowed alternative app marketplaces in the EU from iOS 17.4 (2024).

    Going deeper

    • iPhone OS launched with the first iPhone in 2007, was renamed iOS in 2010, and iPadOS split off as its own name in 2019 (iPadOS 13); since 2025 versions are numbered by year, so iOS 26 followed iOS 18.
    • Secure boot runs Boot ROM → iBoot → kernel, each stage checking Apple's signature; the 2019 checkm8 Boot ROM bug in A5–A11 chips could not be patched by software because the ROM is read-only.
    • Data Protection classes (Complete, Complete Unless Open, Until First User Authentication, None) decide when each file's key is available — after reboot, most data stays locked until the first unlock.
    • BlastDoor (iOS 14) parses iMessage content in a tightly sandboxed process after zero-click spyware such as NSO Group's Pegasus abused message parsing; Lockdown Mode (iOS 16) further cuts the attack surface.
    • With the iPhone 17 family in 2025 Apple introduced Memory Integrity Enforcement, built on Arm's Enhanced Memory Tagging Extension, to block many memory-corruption exploits in hardware.
    • In the EU, iOS 17.4 and later allow alternative app marketplaces and web distribution under the Digital Markets Act, but apps must still be notarised by Apple.
    • Device management uses Apple Business Manager or Apple School Manager for zero-touch enrolment, supervised mode for company-owned devices, and User Enrollment to separate work data on personal devices.

    Common mistakes & misconceptions

    • Assuming 'jailbreaking' only affects the owner — it disables code-signing and sandbox protections, so managed corporate devices block jailbroken phones.
    • Thinking a device passcode and Face ID are the same protection — Face ID is a convenience unlock; the passcode is what derives the encryption keys.
    • Ignoring update lag — most spyware chains exploit already-patched bugs, so prompt iOS updates are the single best defence.

    5.10 Android Architecture, AOSP and Android 16/17¶

    Android is the world's most widely used operating system, running on billions of phones, tablets, TVs, cars and watches. Under the hood it is a Linux kernel plus a hardware abstraction layer, native libraries, the Android Runtime (ART) and a Java/Kotlin framework. Google releases the open-source code as the Android Open Source Project (AOSP); phone makers add their own apps and Google services.

    Think of it like…

    Android is like a franchise restaurant system: Google publishes the recipe book (AOSP), each franchise (Samsung, Xiaomi, Google Pixel) adds its own decor and dishes, and every cook (app) works in a separate kitchen with only the ingredients the manager approved.

    Real-world example

    Arjun, an Android developer at the fictional MetroRide transit company, ships a ticketing app. It targets API 36 (Android 16), uses Live Updates to show 'Bus 42 arrives in 3 min' on the lock screen, asks only for approximate location, and calls the Play Integrity API so the ticket server can reject tampered app copies.

    How it works¶

    1. The device boots with Android Verified Boot checking each partition's signature and dm-verity protecting system data.
    2. The Linux kernel (a Generic Kernel Image plus vendor modules) starts init, which starts native daemons and the Zygote process.
    3. Zygote preloads the Android framework in ART and forks a new process for each app, which gets its own Linux user ID.
    4. Apps call framework services (activity, package, location managers) through Binder inter-process communication.
    5. Framework services reach hardware through HAL interfaces implemented by the device vendor, defined in AIDL.

    Who uses it

    Android app developers, mobile security analysts, device-maker (OEM) engineers, automotive infotainment teams, mobile device management admins and forensic examiners.

    Key takeaway

    Memorise the stack bottom-up: Linux kernel → HAL → native libraries and ART → Java API framework → apps; and that every app is a separate Linux user, enforced further by SELinux.

    Going deeper

    • Android 16 (API 36) reached Pixel phones on 10 June 2025, earlier than usual, followed by Android 17 (API 37) on 16 June 2026; Google now ships a major SDK release in Q2 and a minor SDK update in Q4.
    • ART replaced the Dalvik VM in Android 5.0 (2014); it combines ahead-of-time compilation, a JIT and cloud-delivered baseline profiles so apps start fast without huge install-time compiles.
    • Project Treble (Android 8.0, 2017) separated vendor code behind stable HAL interfaces, Mainline (Android 10) lets Google update core components as APEX modules through Google Play, and the Generic Kernel Image (Android 12, kernel 5.10+) standardises the kernel.
    • Runtime permissions arrived in Android 6.0; later versions added one-time permissions, approximate location, the photo picker and auto-reset of permissions for unused apps.
    • SELinux has been enforcing for all domains since Android 5.0, and file-based encryption plus Android Verified Boot 2.0 are standard on modern devices.
    • From 30 September 2026 Google's developer verification applies to apps installed on certified devices in Brazil, Indonesia, Singapore and Thailand, with global rollout planned for 2027; hobbyists get limited-distribution accounts and power users an advanced flow.
    • Google Play requires apps targeting Android 15+ to support 16 KB memory pages (from November 2025), and the Android Virtualization Framework (pKVM) powers protected VMs and the Linux Terminal app on supported devices.

    Common mistakes & misconceptions

    • Confusing Android with Google's apps — AOSP is open source, but Play Store, Play Services and Gmail are proprietary Google software licensed to device makers.
    • Requesting every permission at install — ask at the moment of need and prefer pickers (photo picker, contacts picker) that need no broad permission.
    • Assuming all Android phones get updates at the same time — OEM and carrier schedules vary widely; check the vendor's support period (Pixel and recent Samsung flagships promise 7 years).

    5.11 ChromeOS, HarmonyOS and Other Device Operating Systems¶

    Beyond Windows, macOS, iOS and Android, several other operating systems run millions of devices: ChromeOS on school laptops, Huawei's HarmonyOS on phones in China, Tizen and webOS on smart TVs, and watch and headset OSes from Apple and Google. Many reuse the Linux kernel; some, like HarmonyOS NEXT and Fuchsia, use their own microkernels.

    Think of it like…

    These systems are like regional car brands built on shared engines: several bolt different bodies onto the same Linux engine, while a few designers decided to build entirely new engines of their own.

    Real-world example

    Ms Okafor runs IT for the fictional Brookside Primary School. Its 450 Chromebooks boot in seconds, update themselves in the background, and are managed from the Google Admin console. When older laptops lose ChromeOS updates, she reinstalls them with ChromeOS Flex, and older pupils use the built-in Linux development environment for a coding club.

    How it works¶

    1. ChromeOS verifies its firmware and read-only system partition at every boot (Verified Boot) and keeps two system partitions (A/B).
    2. Updates install to the inactive partition in the background and take effect on the next restart, so a failed update can roll back.
    3. Web apps, Android apps (in a container or VM) and Linux apps (in the Crostini VM) run side by side, isolated from the core OS.
    4. HarmonyOS NEXT replaces Linux and Android code with Huawei's HongMeng microkernel and native ArkTS apps.
    5. Smaller OSes such as Tizen, webOS and Wear OS adapt Linux or Android to TVs and wearables with their own app models.

    Who uses it

    Education IT administrators, device makers, smart-TV and wearable developers, and engineers working with Chinese markets meet these operating systems.

    Key takeaway

    Remember: ChromeOS = Linux kernel + Chrome browser + Verified Boot + automatic A/B updates, with 10 years of updates for devices released from 2019; Google has announced it is merging ChromeOS into an Android-based platform.

    Going deeper

    • ChromeOS launched on Chromebooks in 2011; it uses a Linux kernel and a Gentoo-based build system, and its Verified Boot checks firmware and the read-only root partition, entering recovery if anything has been modified.
    • Chromebooks released from 2019 onwards receive 10 years of automatic updates; ChromeOS Flex (2022) installs a ChromeOS variant on ordinary x86-64 PCs and Macs but lacks Android apps and some hardware security features.
    • The Linux development environment (Crostini) runs a Debian container inside a VM managed by crosvm on KVM — a good example of virtualisation used for isolation on a consumer OS.
    • In 2025 Google confirmed it is combining ChromeOS and Android into a single platform (codename 'Aluminium'); existing ChromeOS devices continue to receive updates during the transition.
    • HarmonyOS 5 (HarmonyOS NEXT, released late 2024) removed all AOSP code, runs only native apps written in ArkTS with the ArkUI framework, and uses the HongMeng microkernel; HarmonyOS 6 followed in late 2025.
    • OpenHarmony, the open-source base Huawei donated to China's OpenAtom Foundation, supports kernels ranging from LiteOS for tiny devices to Linux, and is used by other Chinese device makers.
    • Google's Fuchsia, built on the Zircon microkernel, replaced the software on first-generation Nest Hub smart displays in 2021, showing a full OS swap delivered as an update.

    Common mistakes & misconceptions

    • Thinking Chromebooks 'cannot run real software' — they run web apps, Android apps and full Linux tools, though not native Windows desktop apps.
    • Assuming HarmonyOS is still 'Android with a new skin' — that was true up to version 4; HarmonyOS 5 and later do not run Android APKs natively.
    • Forgetting a Chromebook's Auto Update Expiration date when buying — check it in Google's support list before purchase.

    5.12 The BSD Family: FreeBSD, OpenBSD and NetBSD¶

    The BSDs are free Unix-like operating systems descended from the Berkeley Software Distribution, created at the University of California, Berkeley from 1977. Unlike Linux distributions, each BSD develops its kernel and core userland together as one complete system, and they use permissive BSD licences that let companies reuse code in closed products.

    Think of it like…

    Linux is like buying a kit car where the engine (kernel) and body (tools) come from different makers; a BSD is a factory car where engine, body and manual are designed together by one team.

    Real-world example

    Hamza, network engineer at the fictional Coastline ISP, builds a firewall on OPNsense (FreeBSD-based) using the PF packet filter, and a storage server on FreeBSD with ZFS and jails isolating each customer service. His colleague uses OpenBSD for the bastion SSH host because of its security-first defaults.

    How it works¶

    1. Install the base system: kernel plus a matching userland released and tested together.
    2. Configure services in /etc/rc.conf (FreeBSD) or with rcctl (OpenBSD).
    3. Add third-party software from ports or binary packages (pkg on FreeBSD, pkg_add on OpenBSD, pkgsrc on NetBSD).
    4. Isolate services with jails (FreeBSD) or restrict programs with pledge and unveil (OpenBSD).
    5. Update the base system with freebsd-update or pkgbase (FreeBSD), syspatch (OpenBSD) or sysupgrade.

    Who uses it

    Network and firewall engineers, storage administrators, embedded and appliance developers, CDN and streaming engineers, and security-minded sysadmins use BSD systems.

    Key takeaway

    Know each BSD's personality: FreeBSD = performance, servers and appliances; OpenBSD = security and correctness (OpenSSH, PF); NetBSD = portability ('Of course it runs NetBSD').

    Going deeper

    • 4.2BSD (1983) introduced the Berkeley sockets API and a TCP/IP stack that shaped almost every networked OS; Windows, Linux and macOS socket APIs still follow that design.
    • Current releases as of October 2026: FreeBSD 15.1 (June 2026) with 14.x still supported, OpenBSD 7.9 (May 2026, the project's 60th release; OpenBSD ships every six months), and NetBSD 11.0 (July 2026).
    • FreeBSD 15 moves towards managing the base system as packages ('pkgbase'), replacing the separate freebsd-update tool over time.
    • FreeBSD jails (2000) isolate processes, file systems and networking with one shared kernel — a precursor of Linux containers; bhyve is FreeBSD's own type-2 hypervisor, and Capsicum provides capability-based sandboxing.
    • OpenBSD pioneered or popularised W^X memory, pledge() and unveil() for self-restricting programs, the PF firewall, LibreSSL and OpenSSH, and ships with only a minimal set of services enabled.
    • Commercial products built on FreeBSD include Sony's PlayStation 4 and 5 system software, Netflix's Open Connect CDN appliances, NetApp ONTAP, pfSense and OPNsense firewalls; macOS's userland also borrows heavily from FreeBSD.
    • The permissive BSD licences (2-clause and 3-clause) allow use in closed-source products without sharing changes, unlike Linux's GPLv2 — one reason vendors choose a BSD base.

    Common mistakes & misconceptions

    • Calling the BSDs 'Linux distributions' — they have different kernels, init systems, tools and licences; Linux binaries need a compatibility layer.
    • Assuming FreeBSD jails equal Docker — jails give isolation, but image formats, registries and orchestration differ (FreeBSD has added OCI container support via tools like Podman).
    • Expecting identical command options — BSD and GNU versions of ls, sed and tar differ, which breaks scripts written only for Linux.

    5.13 Real-Time and Embedded Operating Systems¶

    Most computers in the world are not PCs or phones but tiny controllers inside cars, pacemakers, washing machines and satellites. They run real-time operating systems (RTOSes) or slimmed-down embedded Linux. A real-time OS guarantees that important work finishes within a known deadline, every time — being predictable matters more than being fast.

    Bare metal vs RTOS vs embedded Linux

    Bare metal / RTOS Embedded Linux
    Typical chip microcontroller, no MMU application processor with MMU
    RAM kilobytes to a few MB tens of MB and up
    Boot time milliseconds about 1-10 seconds
    Determinism hard real-time soft; PREEMPT_RT improves it
    Networking, UI, apps limited, add-on stacks full Linux ecosystem
    Examples FreeRTOS, Zephyr, ThreadX Yocto, Buildroot images
    Typical use sensors, motor control, wearables routers, cameras, infotainment

    Pick the smallest system that meets the deadlines and the features you need.

    Think of it like…

    An RTOS is like an air-traffic controller: the job is not to land the most planes per hour but to make sure every plane lands at exactly the right moment, with emergencies always handled first.

    Real-world example

    Sofia, a firmware engineer at the fictional Aquilo Medical, builds an insulin pump. A FreeRTOS task must read the glucose sensor every 5 ms, another drives the motor, and a low-priority task updates the screen. She uses priority inheritance on the shared sensor mutex so the display task can never delay a dose — the same class of bug that once reset NASA's Mars Pathfinder.

    How it works¶

    1. Split the firmware into tasks (threads) and give each a fixed priority according to its deadline.
    2. The RTOS scheduler always runs the highest-priority ready task and preempts lower ones immediately.
    3. Interrupt service routines do minimal work and signal tasks through queues, semaphores or event flags.
    4. Shared resources use mutexes with priority inheritance to avoid unbounded priority inversion.
    5. Measure worst-case execution time and interrupt latency on real hardware, then certify against the industry safety standard.

    Who uses it

    Embedded and firmware engineers, automotive, aerospace and medical-device developers, IoT product teams and safety-assessment engineers.

    Key takeaway

    Interviewers love priority inversion: a low-priority task holds a lock a high-priority task needs while a medium task runs; the fix is priority inheritance or a priority-ceiling protocol.

    Going deeper

    • Hard real-time means a missed deadline is a failure (airbag, pacemaker); soft real-time tolerates occasional misses (video playback); jitter is the variation in response time.
    • FreeRTOS, created by Richard Barry in 2003 and stewarded by Amazon since 2017, is MIT-licensed; its kernel is only a few thousand lines of C and typically compiles to roughly 6-12 KB of flash.
    • Zephyr, a Linux Foundation project since 2016, uses devicetree and Kconfig like Linux; its LTS release is 3.7 (July 2024, supported to 2029) and Zephyr 4.4 shipped in April 2026.
    • BlackBerry QNX Neutrino is a POSIX microkernel RTOS widely used in car digital cockpits and ADAS; Wind River VxWorks flies on NASA Mars rovers and many aircraft and industrial systems.
    • Safety certification drives OS choice: IEC 61508 (industrial), ISO 26262 ASIL levels (automotive), DO-178C (avionics) and IEC 62304 (medical device software); pre-certified variants such as SafeRTOS exist for these markets.
    • The Yocto Project builds custom embedded Linux images from recipes; its LTS releases are 5.0 'Scarthgap' (April 2024, to April 2028) and 6.0 'Wrynose' (April 2026, to April 2030). Buildroot is the simpler alternative.
    • Microsoft's Azure RTOS was contributed to the Eclipse Foundation as Eclipse ThreadX (MIT licence), and Arm announced the end of life of Mbed OS for July 2026, so new projects choose Zephyr, FreeRTOS or ThreadX instead.

    Common mistakes & misconceptions

    • Thinking 'real-time' means 'fast' — it means bounded and predictable; a slow but always-on-time system can be real-time.
    • Using a plain binary semaphore to protect shared data between tasks of different priorities — use a mutex with priority inheritance.
    • Choosing embedded Linux for a hard sub-millisecond control loop — pair it with a microcontroller running an RTOS, or use PREEMPT_RT and measure carefully.

    5.14 OS Security Mechanisms: Exploit Mitigations, Access Control and Trusted Boot¶

    Modern operating systems assume some programs will have bugs and add layers that make those bugs hard to exploit. Memory protections such as ASLR, non-executable memory, stack canaries and control-flow integrity stop common attacks; mandatory access control (SELinux, AppArmor) and sandboxes limit damage; and secure boot plus code signing make sure only trusted code starts in the first place.

    What each mitigation blocks — and how attackers respond

    Blocks Typical bypass
    Stack canary linear stack overflows leaking the canary value
    DEP / NX running injected shellcode return-oriented programming
    ASLR / KASLR hard-coded addresses information-leak bugs
    CFI / shadow stack ROP and JOP hijacks data-only attacks
    SELinux / AppArmor post-exploit file and port access kernel exploits
    Sandboxing renderer reaching the OS sandbox-escape bug chains
    Secure Boot bootkits, unsigned loaders signed but vulnerable loaders

    No single mitigation is enough; they are designed to be layered.

    Think of it like…

    OS security is like protecting a bank: random vault locations (ASLR), walls that cannot become doors (non-executable memory), tamper seals on the safe (stack canaries), guards checking that everyone follows the official route (CFI), and each employee's badge opening only their own rooms (mandatory access control).

    Real-world example

    Kenji, a security engineer at the fictional Orchid Payments, reviews a vulnerable image-parsing library on the company's Linux servers. Because the service is compiled with stack protection and PIE, runs under an SELinux confined domain and a seccomp filter, the public proof-of-concept only crashes the process. Patching is still urgent, but the layers bought time and kept card data safe.

    How it works¶

    1. Secure boot verifies each boot stage's signature so only trusted firmware, boot loaders and kernels start.
    2. The kernel enforces code signing or driver signing and protects itself with KASLR and, on Windows, virtualisation-based security.
    3. Mandatory access control (SELinux, AppArmor) confines each service to the files, ports and capabilities its policy allows.
    4. Sandboxes (seccomp, AppContainer, App Sandbox) further restrict untrusted code such as browser renderers.
    5. Inside every process, ASLR, non-executable memory, stack canaries and CFI make memory-corruption bugs hard to exploit.

    Who uses it

    Security engineers, penetration testers, exploit developers, OS and compiler developers, Linux and Windows hardening specialists and SOC analysts.

    Key takeaway

    Map each mitigation to the attack it stops: canaries → stack overflows; DEP/NX → injected shellcode; ASLR → hard-coded addresses; CFI and shadow stacks → ROP; MAC and sandboxes → post-exploitation access.

    Going deeper

    • ASLR randomises where stacks, heaps, libraries and executables load; PaX introduced it for Linux in 2001, mainline Linux added it in 2005 and Windows in Vista (2007); KASLR applies the idea to the kernel.
    • DEP/NX marks data pages non-executable using the CPU's NX/XD bit (AMD64 in 2003, Windows XP SP2 in 2004); attackers responded with return-oriented programming that chains existing code 'gadgets'.
    • Control-flow integrity checks indirect jumps and returns: Microsoft Control Flow Guard (2015), Clang CFI and kCFI in Linux, Intel CET shadow stacks and indirect branch tracking (Tiger Lake, 2020), and Arm pointer authentication (ARMv8.3) and BTI.
    • SELinux, developed by the NSA and merged into Linux 2.6 in 2003, labels every process and object and enforces type-enforcement policy; AppArmor uses simpler path-based profiles and is the default on Ubuntu and SUSE.
    • Windows virtualisation-based security uses the Hyper-V hypervisor to create an isolated secure kernel; Memory Integrity (HVCI) checks kernel code signatures there, and Credential Guard isolates secrets, on by default on eligible Windows 11 Enterprise devices since 22H2.
    • UEFI Secure Boot (UEFI 2.3.1, 2011) trusts keys in the db and revokes them in dbx; Microsoft's original 2011 Secure Boot certificates expire between June and October 2026, so devices need the 2023 replacement certificates to keep receiving boot-security updates.
    • Memory-safe languages remove whole bug classes: Rust support entered Linux 6.1 (2022) and is used in Android and parts of Windows; Google reported Android's share of memory-safety vulnerabilities falling from 76% in 2019 to 24% in 2024.

    Common mistakes & misconceptions

    • Treating any single mitigation as a fix — attackers chain an information leak to beat ASLR and ROP to beat DEP; patching the bug remains essential.
    • Setting SELinux to permissive or disabled to 'fix' an error — read the AVC denial with ausearch or audit2why and adjust the policy or file labels instead.
    • Assuming Secure Boot stops all boot malware — BlackLotus (2023) abused a signed but vulnerable Windows boot manager, so revocation (dbx) updates matter.
    • Believing code signing means code is safe — signed drivers have been abused in 'bring your own vulnerable driver' attacks; use blocklists too.
