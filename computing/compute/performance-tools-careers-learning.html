    Chapter 8: Performance, Tools, Careers & Learning¶

    Knowing how computers work becomes truly useful when you can measure them, make them faster and turn that skill into a career. This chapter covers fair benchmarking, the main benchmark suites, profiling tools and analysis methods, optimisation, power and cooling, and how to choose a PC or server. It finishes with careers, certifications, books, hands-on projects and model interview answers to take you from student to job-ready.

    8.1 Benchmarking Basics & Pitfalls¶

    A benchmark is a repeatable test that measures how fast a computer or program does a fixed job, so you can compare machines or check whether a change helped. Good benchmarking is surprisingly hard: results wobble from run to run, and a test that does not resemble your real work can point you in the wrong direction. The golden rule is to measure carefully, several times, under controlled conditions.

    Think of it like…

    Benchmarking is like timing runners: you need the same track, the same distance, a proper warm-up and several heats before you can say who is really faster.

    Real-world example

    Leon, an intern at a fictional video start-up called Clipwise, ran a compression test once on two laptops and declared laptop A 30% faster. His mentor made him repeat it ten times after a warm-up run, with both laptops plugged in and cooled. The median times were 41.2 s and 39.8 s, a gap of only about 3.5%, smaller than the run-to-run spread of 2-4%. The first result had been caused by laptop B indexing files in the background.

    How it works¶

    1. Define the question and pick a workload that resembles real use.
    2. Fix the conditions: same software versions, power plan, temperature and background load.
    3. Do warm-up runs, then repeat the measurement many times and record every result.
    4. Report the median (or mean) with the spread, such as standard deviation or min-max.
    5. Compare with ratios and summarise several tests with a geometric mean, never a single cherry-picked number.

    Who uses it

    Hardware reviewers, performance engineers, HPC and cloud teams, and anyone deciding which machine or setting is genuinely faster.

    Key takeaway

    In interviews, mention warm-up, repetition, variance and representative workloads; it shows you know that one run proves nothing.

    Going deeper

    • Common noise sources: turbo and thermal state, background services, CPU frequency governors, memory-layout changes from ASLR, interrupts and busy SMT siblings. Experts pin threads, fix clock speeds and isolate cores for stable results.
    • Report distributions, not single numbers: median and interquartile range resist outliers, and latency results should show p50, p95, p99 and maximum, ideally as a histogram or CDF plot.
    • Optimising compilers can delete work whose result is never used or hoist it out of loops; harnesses provide helpers such as DoNotOptimize (Google Benchmark) and Blackhole (JMH) to prevent this.
    • Summarise ratios with the geometric mean, as SPEC does; an arithmetic mean of ratios gives different answers depending on which machine you choose as the baseline.
    • For load tests, constant-arrival-rate tools such as wrk2 and k6 avoid coordinated omission, whereas closed-loop tools that wait for each reply under-report latency during overload.
    • Continuous benchmarking in CI catches regressions early, but needs dedicated quiet machines — shared cloud CI runners are too noisy for small differences.

    Common mistakes & misconceptions

    • Running a test once and trusting it — repeat it and report the spread.
    • Benchmarking debug builds or with a profiler attached — measure optimised release builds under normal conditions.
    • Comparing a laptop on battery with one on mains power, or hot with cold — fix and record power and thermal state.
    • Averaging speed-up ratios arithmetically — use the geometric mean instead.

    Try it: Time a function properly in Python with repeats and report median and spread¶

    import timeit, statistics
t = timeit.repeat('sum(range(1_000_000))', repeat=10, number=5)
print(f'median {statistics.median(t):.4f}s  stdev {statistics.stdev(t):.4f}s  min {min(t):.4f}s')

    Name What it does Example
    Benchmark
    General performance engineering · Concept · Current · Beginner    		 A standard, repeatable workload run to measure and compare the performance of hardware, software or configurations. Running the same video export on three laptops and comparing the times is a simple benchmark.
    Microbenchmark vs macrobenchmark
    General performance engineering · Concept · Current · Intermediate    		 A microbenchmark times one tiny operation; a macrobenchmark times a whole realistic application or workload. Timing one hash function is a microbenchmark; timing a full web request through the app stack is a macrobenchmark.
    Warm-up run
    General performance engineering · Concept · Current · Beginner    		 Discarded first runs that let caches fill, JIT compilers optimise and CPU clocks settle before real timing starts. A Java service is run for 60 seconds before measuring, so the JIT has compiled hot methods.
    Run-to-run variance
    Statistics · Metric · Current · Beginner    		 The natural spread of results between identical runs, caused by background tasks, temperature, turbo behaviour and memory layout. Ten runs of a render range from 52 to 55 seconds; any claimed gain under about 3 seconds is noise.
    Median and percentiles
    Statistics · Metric · Current · Intermediate    		 The median is the middle result; percentiles like p99 show the worst typical cases, which matter for latency. An API averages 20 ms, but its p99 is 400 ms, so one request in a hundred feels slow.
    Geometric mean
    Statistics; used by SPEC · Metric · Current · Intermediate    		 The nth root of the product of n ratios; the fair way to combine speed-up ratios from several tests. Speed-ups of 2x and 0.5x give a geometric mean of 1.0x, correctly showing no overall gain.
    Representative workload
    General performance engineering · Concept · Current · Beginner    		 A test that uses data sizes, access patterns and operations similar to the real job you care about. A database team benchmarks with a copy of last month's real query log instead of a toy table.
    Confidence intervals and significance
    Statistics · Metric · Current · Intermediate    		 A range likely to contain the true result; if two configurations' intervals overlap heavily, the apparent difference may just be noise. Build A takes 41.2 ± 0.9 s and build B 40.8 ± 1.1 s at 95% confidence — there is no real winner.
    Throughput vs latency
    General performance engineering · Concept · Current · Beginner    		 Report both: throughput (operations per second at full load) and latency at a stated load, because one number hides the trade-off. Batching AI requests raises tokens per second but makes each user wait slightly longer for the first word.
    Thermal and power state control
    General performance engineering · Concept · Current · Intermediate    		 Laptop power plans, turbo boost and heat change clock speeds, so they must be fixed and recorded during tests. A laptop scores 15% lower on battery than on mains power, so reviewers test both and label them.
    Benchmarketing
    Industry slang · Concept · Current · Beginner    		 Vendor charts that pick flattering tests, settings or scales so a product looks better than real-world use would show. A slide shows a bar chart starting at 90 instead of 0, making a 4% lead look like double.
    Coordinated omission
    Term popularised by Gil Tene · Concept · Current · Advanced    		 A load-testing mistake where slow responses delay new requests, so the tool silently under-reports bad latency. A tester switches to a constant-rate load generator and finds p99 latency is ten times worse than first reported.
    Reproducibility record
    General performance engineering · Concept · Current · Intermediate    		 Writing down hardware, firmware, OS, compiler, flags, settings and raw results so anyone can repeat the test. Each result in a team spreadsheet lists BIOS version, kernel, gcc flags and the ten raw timings.
    hyperfine and benchmark harnesses
    hyperfine (David Peter); Google Benchmark; JMH (OpenJDK); Criterion.rs; pytest-benchmark · Tool · Current · Intermediate    		 Tools that handle warm-up, repetition and statistics for you, from whole commands (hyperfine) to single functions in C++, Java, Rust or Python. 'hyperfine --warmup 3 ./old ./new' reports each command's mean and spread, and how many times faster the new build is.

    8.2 Benchmark Suites You Will Meet¶

    Instead of inventing your own tests, you can use well-known benchmark suites that everyone recognises, so results can be compared across the world. Some target desktop users (Geekbench, Cinebench, 3DMark), some target servers and supercomputers (SPEC, HPL, STREAM) and some target AI systems (MLPerf). Each one measures something specific, so you must know what a score really means before trusting it.

    Think of it like…

    Benchmark suites are like standardised school exams: everyone sits the same paper, so marks can be compared, but a maths exam says nothing about how well you sing.

    Real-world example

    Aisha is choosing between two cloud server types for a fictional engineering firm, Ridgeway Analytics. She checks published SPEC CPU rate results for raw compute, runs STREAM to compare memory bandwidth, and uses fio to test the attached storage. One server wins SPEC by 12% but loses STREAM by 25%; because Ridgeway's simulations are memory-bound, she picks the second server.

    How it works¶

    1. Decide what you care about: single-thread speed, multi-core throughput, graphics, memory, storage or AI.
    2. Pick the suite designed for that question and use its official rules and settings.
    3. Run it several times on an otherwise idle, well-cooled machine.
    4. Compare only scores from the same suite version, because new versions reset the scale.
    5. Cross-check with a test of your own real workload before spending money.

    Who uses it

    Reviewers, system buyers, cloud and HPC architects, chip vendors' marketing and engineering teams, and students comparing laptops.

    Key takeaway

    Never compare scores across versions: Geekbench 6 vs 7 or Cinebench 2024 vs 2026 numbers are on different scales.

    Going deeper

    • SPEC CPU 2017 contains 43 benchmarks in four suites — SPECspeed and SPECrate, each integer and floating point. 'Base' results require consistent compiler flags; 'peak' allows per-benchmark tuning.
    • SPEC scores are ratios against a fixed reference machine, combined with a geometric mean; published results must follow the run rules and are reviewed before appearing on spec.org.
    • MLPerf Inference defines scenarios — SingleStream, MultiStream, Server (latency-bounded queries) and Offline (batch throughput) — and 'closed' (same model and accuracy) versus 'open' divisions.
    • STREAM's arrays must be much larger than all caches combined (the documented rule of thumb is at least four times), otherwise you measure cache rather than DRAM bandwidth; Triad is the figure usually quoted.
    • fio essentials: direct=1 bypasses the page cache, iodepth sets queue depth, and SSDs should be preconditioned before testing random 4 KiB and sequential large-block patterns separately.
    • Consumer suites use short runs that can miss throttling; Cinebench's 10-minute mode or looped 3DMark stress tests reveal sustained behaviour and cooling quality.

    Common mistakes & misconceptions

    • Comparing scores across versions or settings — Geekbench 6 vs 7, SPEC base vs peak and Cinebench 2024 vs 2026 are different scales.
    • Treating one suite as 'overall speed' — each measures one type of workload.
    • Trusting vendor-run results without reading the configuration — compiler flags, memory and power settings can swing scores widely.

    Try it: Run quick, harmless CPU and storage benchmarks on Linux¶

    sudo apt install sysbench fio
sysbench cpu --threads=4 run
fio --name=randread --rw=randread --bs=4k --size=256M --runtime=30 --time_based --filename=/tmp/fiotest
rm /tmp/fiotest

    8.3 Profiling & Monitoring Tools¶

    A profiler shows where a program spends its time, so you can fix the slow part instead of guessing. Monitoring tools show what the whole machine is doing right now: how busy the CPU, memory, disks, network and GPU are. Together they turn 'it feels slow' into a clear picture of the real bottleneck.

    Think of it like…

    A profiler is like a fitness tracker for code that shows which exercise tires you most, while monitoring tools are the dashboard gauges of a car.

    Real-world example

    Tomás, a back-end developer at a fictional ticket site called Gatehouse, saw checkout requests take 900 ms. htop showed one CPU core pinned at 100%, so he ran 'perf record' and drew a flame graph. 70% of the time was spent re-parsing a config file on every request. Caching it once cut checkout time to 120 ms.

    How it works¶

    1. Start broad with a monitor (htop, Task Manager, nvidia-smi) to see which resource is busy.
    2. Use a sampling profiler (perf, VTune, uProf, Instruments) to find the hottest functions.
    3. Visualise the call stacks, for example as a flame graph, to see which path is expensive.
    4. Drill into hardware counters or a GPU profiler (Nsight Systems, then Nsight Compute) if the hot spot is still unclear.
    5. Fix one thing, then measure again with the same tools to confirm the gain.

    Who uses it

    Software, performance, SRE, HPC, game and GPU engineers, plus sysadmins who must explain why a server is slow.

    Key takeaway

    Learn 'perf stat', 'perf record' and 'perf report' plus flame graphs; they appear in almost every Linux performance interview.

    Going deeper

    • Sampling profilers such as perf interrupt the program (for example 99 times per second per CPU) and record stacks with low overhead; instrumenting tools like gprof and Callgrind count every call but can slow programs dozens of times.
    • Useful stacks need symbols and frame pointers: build with -g and -fno-omit-frame-pointer, or use DWARF or LBR unwinding. Fedora and Ubuntu 24.04 re-enabled frame pointers by default to make profiling easier.
    • Hardware performance counters (cycles, instructions, cache and branch misses) come from the CPU's PMU; 'perf stat' reads them cheaply, and multiplexes when you request more events than there are counters.
    • CPU profilers cannot see time spent waiting on locks, disk or network; off-CPU tools such as BCC's offcputime or wall-clock profilers reveal it.
    • nvidia-smi 'utilisation' only means a kernel was running, not that the GPU's SMs were busy; DCGM and Nsight metrics such as SM occupancy and memory throughput show real efficiency.
    • Modern observability combines metrics (Prometheus), logs, traces and profiles; OpenTelemetry, a CNCF project, standardises how traces, metrics and logs are collected.

    Common mistakes & misconceptions

    • Profiling a debug build — optimisation changes hot spots; profile release builds compiled with symbols.
    • Reading 100% GPU utilisation as 'fully efficient' — it only means some kernel was running.
    • Profiling too short a run or an unrealistic input — collect enough samples on a representative workload.

    Try it: Profile a program with Linux perf and watch a GPU live¶

    perf stat -e cycles,instructions,cache-misses ./prog     # counters + IPC
perf record -g ./prog && perf report                     # hottest functions
htop                                                     # live CPU/memory view
nvidia-smi dmon -s pucm                                  # GPU power, util, clocks, memory

    8.4 Performance Analysis Methods¶

    Performance analysis methods are step-by-step ways of thinking that stop you from wasting time on random fixes. They help you answer two questions: which resource is the bottleneck, and how much faster could things get if you fixed it. The first rule of all of them is simple: measure first, then optimise.

    Think of it like…

    It is like a doctor's examination: check vital signs in a fixed order before deciding on treatment, rather than guessing from one symptom.

    Real-world example

    Mei, an HPC engineer at the fictional Northvale Weather Centre, was asked to speed up a forecast model. Applying the USE method, she found memory bandwidth near saturation while CPU cores sat 40% stalled. A roofline plot confirmed the main kernel's arithmetic intensity was only 0.3 FLOP per byte, so faster cores would not help. Restructuring loops to reuse cached data raised intensity and cut run time by 35%.

    How it works¶

    1. Measure first: profile to find the hot spot that dominates run time.
    2. Check each resource for utilisation, saturation and errors (the USE method).
    3. Use Amdahl's law to estimate the best possible gain before investing effort.
    4. Place the hot kernel on a roofline chart to see if it is compute-bound or memory-bound.
    5. For CPU code, use top-down analysis to see whether the front end, back end or bad speculation is to blame.

    Who uses it

    Performance engineers, HPC specialists, SREs, compiler and CPU architects, and any developer handed a 'make it faster' ticket.

    Key takeaway

    Learn the USE checklist and the queueing knee: a resource at 90% utilisation already makes requests wait about ten times their service time, which is why healthy systems keep headroom.

    Going deeper

    • Gregg's 'Linux performance analysis in 60 seconds' uses commands such as uptime, dmesg, vmstat 1, mpstat -P ALL 1, pidstat 1, iostat -xz 1, free -m, sar -n DEV 1 and top for a fast first USE pass.
    • Top-down level 1 splits pipeline slots into Retiring, Bad Speculation, Front-End Bound and Back-End Bound, with Back-End split into Memory-Bound and Core-Bound; 'perf stat --topdown' and VTune report it.
    • Little's law (L = λW) holds for any stable system and drives capacity planning: 10,000 requests per second at 50 ms each means about 500 requests in flight at once.
    • Characterise the workload first — who causes the load, which operations, what sizes and mix; many 'performance bugs' turn out to be unexpected load such as a bot or a retry storm.
    • Tail at scale (Dean and Barroso, 2013): if a request fans out to 100 servers that are each slow 1% of the time, about 63% of requests hit at least one slow server.
    • Amdahl's and Gustafson's laws, covered in earlier chapters, set the ceiling for any fix: estimate the possible gain before investing days of effort.

    Common mistakes & misconceptions

    • Optimising without a target — define the metric and what 'good enough' means first.
    • Watching only averages — tail latency and saturation hide behind a healthy mean.
    • Changing several things at once — you cannot tell which change helped or hurt.
    • Assuming high CPU means the CPU is the problem — spinning locks and memory stalls also look like busy CPU.

    Try it: The queueing knee and a roofline check in Python¶

    S = 0.010                       # service time: 10 ms
for U in (0.5, 0.8, 0.9, 0.95):  # utilisation
    print(f'{U:.0%} busy -> response ~ {S/(1-U)*1000:.0f} ms')

    8.5 Optimisation Basics¶

    Optimisation means making a program use less time, memory or energy while giving the same answers. The biggest wins usually come from a better algorithm, then from arranging data so the CPU's caches and vector units are used well, and only then from compiler flags, parallel threads or a GPU. Always keep a correct, measured baseline so you know each change really helped.

    Think of it like…

    Optimising is like planning a supermarket trip: choosing the right shop (algorithm) matters most, then a sensible route down the aisles (memory layout), and only then walking faster (compiler tricks).

    Real-world example

    Kofi, a student at a fictional robotics club, had a collision checker that compared all 20,000 objects with each other: 200 million pairs, taking 14 s. Switching to a spatial grid cut checks to about 300,000 and time to 0.4 s. Storing positions as separate x, y and z arrays (SoA) and compiling with -O3 -march=native let the compiler vectorise the loop, dropping time to 0.15 s. Adding OpenMP across 8 cores brought it to 0.03 s.

    How it works¶

    1. Measure a correct baseline and find the hot spot.
    2. Improve the algorithm and data structures first (lower big-O complexity).
    3. Make memory access cache-friendly: contiguous arrays, sequential access, tiling, SoA layout.
    4. Let the compiler help: -O2/-O3, -march=native, then PGO and LTO, and check its vectorisation report.
    5. Parallelise with threads or OpenMP, avoiding false sharing, and offload suitable work to a GPU.
    6. Re-measure after every change and keep tests to prove results are still correct.

    Who uses it

    Software, game, HPC, embedded, quant-finance and ML engineers, and compiler developers.

    Key takeaway

    Say 'algorithm first, then memory, then parallelism' in interviews, and quote Knuth: premature optimisation wastes effort when you have not measured.

    Going deeper

    • Typical order of wins: algorithms and data structures (often 10-1000×), memory layout and locality (2-10×), vectorisation (up to the SIMD width, e.g. 8 floats with AVX2) and threads (up to the core count).
    • -O2 is the usual release default; -O3 adds more aggressive inlining and vectorisation. -march=native, or a level such as x86-64-v3, enables AVX2 — ship builds targeting the oldest CPUs you support.
    • PGO plus LTO commonly gives several to around 15 per cent on large, branchy programs such as browsers, compilers and databases; post-link optimisers like LLVM BOLT can add more by reordering hot code.
    • Swapping the default malloc for jemalloc or mimalloc can speed up allocation-heavy multithreaded servers and reduce memory fragmentation.
    • Data-oriented design, popular in game engines, organises data by how it is processed, giving contiguous arrays that suit caches and SIMD.
    • Guard correctness: keep unit tests and golden outputs, allow tolerances when floating-point order changes, and run sanitizers (ASan, UBSan, TSan) after risky optimisations.

    Common mistakes & misconceptions

    • Micro-optimising before profiling — the slow code is rarely where you guess.
    • Using -ffast-math or -march=native blindly — results or portability can change silently.
    • Hand-writing what a library already does — tuned BLAS and FFT libraries are very hard to beat.
    • Testing only one input size — caches change the picture between small and large inputs.

    8.6 Power, Thermals & TDP¶

    Every chip turns the electricity it uses into heat, and if that heat is not removed the chip slows itself down to stay safe. TDP and related power limits tell you roughly how much heat a cooler must handle and how hard a processor is allowed to boost. Performance per watt, how much work you get for each unit of energy, now matters as much as raw speed, from phones to AI data centres.

    Think of it like…

    A processor is like a sprinter: it can run flat out for a short burst (turbo), but over a long race it must settle to a pace its body can cool (sustained power).

    Real-world example

    Ravi's fictional design studio, Lumen & Line, bought two identical workstations, but one rendered 18% slower. Monitoring showed its CPU hitting 100 °C and throttling because the cooler had been fitted without enough thermal paste. After re-seating the cooler, temperatures fell to 82 °C and clocks held steady. The studio then capped package power at 200 W instead of 250 W, losing only about 4% speed while cutting noise noticeably.

    How it works¶

    1. The chip draws power; almost all of it becomes heat in a very small area.
    2. The firmware allows short bursts above the sustained limit (turbo) while temperature and current permit.
    3. Heat moves through the heat spreader and thermal paste into a heatsink, liquid loop or cold plate.
    4. Fans or pumps carry heat away into the room air or, in data centres, into facility water.
    5. If temperature or power limits are reached, clocks drop (throttling) to protect the chip.

    Who uses it

    PC builders, laptop designers, data-centre and HPC engineers, chip power architects and anyone sizing cooling or power supplies.

    Key takeaway

    Remember that TDP is a cooling guideline, not the maximum power draw; modern CPUs and GPUs can exceed it briefly.

    Going deeper

    • Dynamic power ≈ C × V² × f. Because voltage must rise with frequency, the last few hundred MHz cost disproportionate power — which is why modest undervolts or power caps lose little performance.
    • Intel lists Processor Base Power and Maximum Turbo Power (125 W and 250 W for the Core Ultra 9 285K); motherboard defaults sometimes exceed them, so reviews may not match stock behaviour.
    • On AMD's AM4/AM5 desktop chips, PPT is about 1.35 × TDP: 65 W → 88 W, 105 W → 142 W, 120 W → 162 W and 170 W → 230 W.
    • RAPL energy counters (Intel since Sandy Bridge, AMD on Zen) are readable through Linux powercap in /sys/class/powercap or with 'perf stat -e power/energy-pkg/', so you can report joules per job.
    • Thin laptops often sustain around 15-30 W while thick gaming laptops sustain 45 W or more; skin temperature and fan noise limits, not just Tjmax, decide the policy.
    • Turbo, DVFS and thermal throttling mechanics are explained in the processors chapter; this section focuses on measuring, sizing and cooling for real machines.

    Common mistakes & misconceptions

    • Treating TDP as maximum draw — CPUs and GPUs exceed it during boost; size power supplies and coolers on real peaks.
    • Panicking at 90-95 °C under load — many modern CPUs are designed to boost until they reach that limit.
    • Comparing laptops by processor name alone — sustained power settings matter more.
    • Leaving the protective film on a new cooler's base — a classic cause of instant overheating.

    8.7 Building or Choosing a PC¶

    A PC is a set of parts that must fit together: processor, motherboard, memory, graphics card, storage, power supply, case and cooling. Choosing well means matching parts to what you actually do (gaming, coding, video, AI) and making sure nothing holds the rest back. You also decide between a laptop's portability and a desktop's power, upgradability and cooling.

    Think of it like…

    Building a PC is like assembling a team: a star striker (GPU) is wasted if the midfield (CPU) and defence (power supply and cooling) cannot keep up.

    Real-world example

    Zara, a computing student, has a budget of about 1,200 pounds for coding and 1440p gaming. She chooses a mid-range 6- to 8-core CPU on a current socket, a B-series motherboard, 32 GB of DDR5 in two sticks, a 1 TB NVMe SSD, a mid-range current-generation GPU and a quality 750 W ATX 3.1 power supply. Benchmarks show her games are GPU-bound, so the money saved on the CPU went where it mattered. Two sticks of RAM keep dual-channel bandwidth.

    How it works¶

    1. List your workloads and budget, and decide laptop or desktop.
    2. Pick the CPU and a compatible motherboard (same socket, suitable chipset).
    3. Add RAM in matched pairs, NVMe storage and a GPU sized for your games or AI work.
    4. Size a quality power supply with headroom and the right GPU connectors.
    5. Choose a case and cooler that fit the parts and keep temperatures sensible.
    6. After building, update BIOS, enable XMP/EXPO memory profiles and stress-test temperatures.

    Who uses it

    Students, gamers, creators, IT technicians and anyone advising friends, family or a small office on hardware.

    Key takeaway

    Check socket, chipset, RAM type, case clearance and power connectors before buying; compatibility mistakes cause most failed builds.

    Going deeper

    • On AMD's AM5 the CPU provides 24 usable PCIe 5.0-capable lanes (x16 for graphics plus two x4 NVMe links), while the chipset adds more lanes, USB and SATA over a narrower uplink.
    • Two DDR5 sticks (one per channel) usually run fastest; four sticks often force lower speeds. DDR5-6000 means 6,000 MT/s, with an actual clock of 3,000 MHz.
    • Size a power supply by adding CPU and GPU peak power plus about 100 W for everything else, then 20-30% headroom; ATX 3.x units are designed to ride through short GPU power spikes.
    • After building, stress-test: MemTest86+ for memory, Cinebench or Prime95 for the CPU and looped 3DMark for the GPU, while watching temperatures in HWiNFO.
    • Prebuilt PCs include a warranty and support but may cut corners on RAM speed, power supply quality or airflow; self-builds give control but you do your own troubleshooting.
    • Upgrade paths depend on platform longevity (AMD has supported AM5 across several CPU generations), spare RAM and M.2 slots, and power-supply headroom.

    Common mistakes & misconceptions

    • Pairing a high-end GPU with a cheap, unrated power supply — buy a quality ATX 3.x unit with native connectors.
    • Forgetting to enable XMP or EXPO — memory then runs at slower default speeds.
    • Not pushing the 12V-2x6 plug fully home, or bending it sharply — it can overheat.
    • Ignoring case clearance — check GPU length and cooler height before buying.

    Servers and workstations are built for reliability and heavy, continuous work rather than looks or gaming. Choosing one means balancing performance, reliability, space, power and total cost, including whether renting in the cloud is cheaper.

    • AMD EPYC 9005 offers up to 192 cores and 12 DDR5 channels per socket; Intel Xeon 6 offers up to 128 performance cores (6900P) or 288 efficient cores (6900E), also with 12 channels on top models.
    • Server reliability goes beyond ECC: patrol scrubbing, chipkill-style multi-bit correction, PCIe error containment and predictive-failure alerts recorded in the BMC's event log.
    • Enterprises usually refresh servers every three to six years; newer, denser machines can replace several old ones and cut power and licence bills, while refurbished servers suit labs and homelabs.
    • Workstation platforms (Threadripper PRO, Xeon W) provide many cores, eight memory channels and plenty of PCIe lanes for multi-GPU rigs, plus ISV-certified drivers for CAD and simulation.
    • 8-GPU HGX servers for AI training can draw over 10 kW each, needing high-power racks, often liquid cooling and several 400 Gb/s network links per node.
    • Security baseline: Secure Boot, TPM 2.0, signed firmware, a silicon root of trust in the BMC, and an isolated management network that never faces the Internet.

    Common mistakes & misconceptions

    • Exposing BMC web interfaces to the Internet — keep them on a separate management network and patch their firmware.
    • Leaving memory channels empty to save money — bandwidth drops sharply for memory-bound workloads.
    • Ignoring software licensing when choosing core counts — licences can cost more than the hardware.
    • Running critical systems without a support contract — waiting days for parts means days of downtime.

sudo ipmitool sel list | tail         # hardware event log

    8.9 Careers in Computing Systems¶

    Knowing how computers really work opens many careers, from designing chips to keeping huge cloud and AI systems running. Some jobs are close to the hardware (chip design, firmware, data-centre work), while others are about software that squeezes the best out of hardware (kernels, GPU programming, performance and reliability). Most share the same core skills: computer architecture, operating systems, Linux, programming and careful measurement.

    Think of it like…

    The computing industry is like a city: some people design the buildings (architects), some build and wire them (hardware and firmware engineers), and some keep the lights on and traffic flowing (sysadmins, SREs and data-centre technicians).

    Real-world example

    Jamal studied computer science and enjoyed his architecture module most. In his final year he built a RISC-V core on a cheap FPGA and profiled CUDA code on a free cloud notebook, putting both on GitHub. He landed a graduate role as a performance engineer at a fictional cloud firm, Stratacloud, tuning servers. Two years later he moved into ML infrastructure, managing GPU clusters for model training.

    How it works¶

    1. Learn the core: programming (C/C++ and Python), computer architecture, operating systems and Linux.
    2. Pick a direction: hardware design, low-level software, HPC/AI infrastructure or operations.
    3. Build visible projects and contribute to open source in that direction.
    4. Add a relevant certification or course if targeting IT and cloud roles.
    5. Apply for internships and graduate roles, and practise explaining your projects clearly.

    Who uses it

    Students choosing a specialism, career changers and early-career engineers planning their next move.

    Key takeaway

    Employers value a working project you can explain in depth more than a long list of buzzwords on a CV.

    Going deeper

    • Chip-design roles usually expect an electrical or computer engineering degree, often a master's; software-side roles (kernel, performance, cloud) welcome computer science graduates and strong self-taught portfolios.
    • IT support and data-centre technician jobs are common entry routes; many cloud engineers and SREs started there and moved up after a few years of hands-on experience.
    • Demand in 2025-26 is driven by AI data-centre build-outs (GPU cluster engineers, technicians, power and cooling specialists), custom silicon at hyperscalers and the growing RISC-V ecosystem.
    • Interviews across these roles probe architecture (caches, pipelines), operating systems (processes, virtual memory), C/C++ or Python, Linux skills and a debugging story from your own project.
    • Strong portfolio signals include measured GitHub projects, open-source contributions (Linux kernel, LLVM, OpenBMC, Zephyr), Student Cluster Competition entries and clear technical write-ups.
    • Titles vary: 'performance engineer' may mean load testing at one company and CPU microarchitecture analysis at another — read the responsibilities, not just the title.

    Common mistakes & misconceptions

    • Collecting certificates without projects — employers want evidence you can build and debug real systems.
    • Assuming hardware careers need a PhD — many RTL, verification and firmware roles hire bachelor's graduates.
    • Neglecting communication — explaining trade-offs clearly is assessed in nearly every interview.

    8.10 Certifications & Courses¶

    Certifications are exams that prove you know a defined set of skills, and many employers use them to filter CVs, especially for IT, Linux and cloud roles. University courses, many free online, teach the deeper theory of how computers work. A sensible plan mixes one or two certifications with solid courses and hands-on projects.

    Think of it like…

    A certification is like a driving licence that proves you passed a standard test, while courses and projects are the hours of real driving that make you good.

    Real-world example

    Hannah worked in retail and wanted an IT career. She passed CompTIA A+ in four months, then took Linux+ while building a home lab. Her first job was desktop support at a fictional council, Westbrook District. A year later she earned AWS Certified Cloud Practitioner and then Solutions Architect - Associate, moving into a junior cloud engineer role.

    How it works¶

    1. Choose a target role, then list the certifications that job adverts for it mention.
    2. Start with a foundation (A+, a cloud fundamentals exam or an NVIDIA associate exam).
    3. Study with official objectives, a course and plenty of hands-on labs.
    4. Book the exam once practice tests are consistently comfortable, and note renewal rules.
    5. Back the certificate with a portfolio project that uses the same skills.

    Who uses it

    Students, career changers, IT staff seeking promotion and employers checking baseline skills.

    Key takeaway

    Exam codes change every few years, so always check the vendor's site for the current version before buying study materials.

    Going deeper

    • Formats differ: CompTIA and most cloud exams use multiple choice plus some performance-based tasks, while Red Hat and Linux Foundation exams are entirely hands-on in live systems — harder but highly respected.

    • Using exam 'dumps' — they break exam agreements, can get certifications revoked and leave you unable to do the job.
    • Buying study material for a retired exam version — check the current exam code on the vendor's site first.
    • Stacking many fundamentals badges — one foundation, one hands-on associate certification and real projects impress more.

    Students, self-taught programmers, interview candidates and working engineers refreshing fundamentals.

    8.12 Hands-On Projects & Lab Ideas¶

    The fastest way to really understand computers is to build and measure things yourself. Many great projects are free or cheap: simulate a CPU, program a small FPGA, cluster a few single-board computers or run GPU code in a free online notebook. Finished projects also make an excellent portfolio for interviews.

    Think of it like…

    Reading about computers without building anything is like learning to swim from a book; projects are getting into the pool.

    Real-world example

    Ethan, a first-year student, spent one term on three projects. He built an 8-bit CPU in the free Digital simulator, benchmarked his laptop's memory bandwidth with a short NumPy script (about 18 GB/s on a single thread), and ran a CUDA matrix multiply on a free cloud GPU notebook that was 40 times faster than his plain Python loop. He wrote up each one on GitHub with graphs, and an interviewer spent most of his interview asking about them.

    How it works¶

    1. Pick a project that matches the career direction you are curious about.
    2. Start small and get a minimal version working end to end.
    3. Measure results (speed, resource use) and record them in a table or graph.
    4. Write a short README explaining what you built, what you measured and what you learned.
    5. Publish it (for example on GitHub) and be ready to discuss it in interviews.

    Who uses it

    Students, self-learners and job-seekers building a portfolio for hardware, systems, HPC or cloud roles.

    Key takeaway

    Always include numbers and graphs in your write-up; 'it got 3.2x faster because of X' is far more impressive than 'I optimised it'.

    Going deeper

    • A strong write-up states the question, method, hardware and software versions, results with graphs and error bars, and an explanation linking the results to theory such as caches or Amdahl's law.
    • Cheap hardware goes far: iCE40 FPGA boards cost tens of dollars with fully open toolchains (Yosys, nextpnr), Pico boards cost a few dollars, and used office mini-PCs make excellent homelab nodes.
    • Free compute: Google Colab and Kaggle notebooks give limited free GPU time, while cloud free tiers and student credits cover small experiments — set budget alerts first.
    • Simulators avoid buying hardware: Verilator for Verilog, QEMU for whole systems including RISC-V, gem5 for architecture research and Wokwi for online microcontroller projects.
    • When contributing upstream, start with small fixes, follow the project's contribution guide, include benchmark evidence with performance patches and expect several review rounds.

    Common mistakes & misconceptions

    • Starting too big, such as an out-of-order CPU first — finish a small working version, then extend it.
    • Publishing results without method or raw data — readers and interviewers cannot trust them.
    • Leaving cloud resources running after an experiment — set budget alerts and delete everything afterwards.

    Try it: A STREAM-like memory bandwidth test with NumPy¶

    import numpy as np, time
n = 50_000_000                      # ~400 MB per array
a = np.ones(n); b = np.ones(n); c = np.empty(n)
for _ in range(3):
    t = time.perf_counter(); np.add(a, b, out=c); dt = time.perf_counter() - t
    print(f'Add bandwidth: {3*8*n/dt/1e9:.1f} GB/s')   # 2 reads + 1 write

    8.13 Interview Questions & Model Answers¶

    Technical interviews for systems, hardware, HPC and cloud jobs repeat a core set of questions about how computers work. Short, clear answers with an example show real understanding. Each item below is a common question, a short model answer and a hint on how to say it well.

    Think of it like…

    Preparing these is like learning the key moves before a match: you will not know every play, but the basics come up every time.

    Real-world example

    In her interview at a fictional chip start-up, Ola was asked what happens on a cache miss. She explained the lookup, the request to the next level, the line fill and the restart, then added that out-of-order cores keep working on other instructions meanwhile. She finished with a real example from her cache-stride experiment. The interviewer moved straight on to harder questions, a good sign.

    How it works¶

    1. Listen for what the question is really testing (concept, trade-off or debugging approach).
    2. Give a one-sentence definition first.
    3. Explain how it works in two or three steps.
    4. Add a trade-off, number or real example from your own projects.
    5. If unsure, reason aloud from first principles rather than guessing silently.

    Who uses it

    Anyone interviewing for software, systems, hardware, HPC, cloud or ML infrastructure roles.

    Key takeaway

    Practise answering aloud in under one minute, then be ready for the follow-up 'why?' or 'what would you measure?'.

    Going deeper

    • Use STAR (Situation, Task, Action, Result) for behavioural and project questions, and keep technical answers to about a minute before inviting follow-ups.
    • Numbers worth knowing: L1 hit about 1 ns, DRAM about 100 ns, NVMe read tens of microseconds, same-data-centre round trip about 0.5 ms, intercontinental 100 ms or more; cache line 64 bytes; page 4 KiB.
    • Debugging questions reward method: state a hypothesis, the tool you would use (top, vmstat, iostat, perf, strace), the evidence you expect and how you would confirm the fix.
    • Hardware interviews often include whiteboard design — a FIFO, a cache lookup, a pipeline hazard diagram or a finite-state machine in Verilog — so practise drawing them.
    • Prepare questions for the interviewer about the team's hardware, tools, on-call duties and how performance or reliability is measured; it signals genuine interest.

    Common mistakes & misconceptions

    • Bluffing when unsure — say what you know and reason aloud; honest reasoning scores better.
    • Reciting definitions without examples — tie answers to numbers or your own projects.
    • Jumping straight to a fix in debugging questions — gather data and narrow the cause first.

    Key chips, architectures, standards, tools & concepts¶

    Name What it does Example
    What happens when a cache miss occurs?
    Computer architecture · Concept · Current · Intermediate    		 The CPU fetches the missing line from the next cache level or memory, stores it, possibly evicting another, then completes the access. Mention the 64-byte line, latency rising from about a nanosecond to around 100 ns, and that out-of-order cores keep working meanwhile.
    Process vs thread?
    Operating systems · Concept · Current · Beginner    		 A process has its own address space; threads within a process share memory but have separate stacks and registers. Say: processes isolate, threads share. Browsers use separate processes per site for safety and threads inside each for speed.
    Explain virtual memory.
    Operating systems · Concept · Current · Intermediate    		 Each process sees its own private address space; page tables and the TLB map virtual pages to physical memory or disk. Add that it gives isolation and lets programs use more memory than RAM, at the cost of page faults.
    Why are GPUs fast for AI?
    GPU architecture · Concept · Current · Beginner    		 AI is mostly huge matrix multiplications; GPUs run thousands of parallel lanes with tensor cores and very high-bandwidth memory. Contrast with CPUs: few powerful cores for branchy code versus many simple lanes for identical maths on lots of data.
    Latency vs bandwidth?
    Performance fundamentals · Concept · Current · Beginner    		 Latency is how long one item takes to arrive; bandwidth is how much data arrives per second. Use a motorway analogy: speed limit is latency, number of lanes is bandwidth; HBM has huge bandwidth, not lower latency.
    What is Amdahl's law?
    Gene Amdahl · Concept · Current · Intermediate    		 Speed-up from parallelising is limited by the serial fraction: with 10% serial, maximum speed-up is 10x. Write the formula and work an example; then mention Gustafson's law for growing problem sizes.
    What does a branch misprediction cost?
    CPU microarchitecture · Concept · Current · Intermediate    		 The pipeline must discard speculative work and restart from the correct path, wasting roughly 10-20 cycles on modern cores. Mention sorted data making branches predictable, and branchless code or lookup tables as fixes.
    What happens when you type a command and press Enter?
    Operating systems · Concept · Current · Intermediate    		 The shell parses it, forks a child process, execs the program, the kernel loads it and schedules it, and output returns through system calls. Name fork, exec, wait and system calls; interviewers love candidates who mention the dynamic loader.
    What is false sharing?
    Multicore programming · Concept · Current · Advanced    		 Threads updating different variables on the same cache line make cores repeatedly invalidate each other's caches. Give the fix: pad or align per-thread data to separate cache lines, then show the before and after timing.
    How would you find why a server is slow?
    Performance methodology · Concept · Current · Intermediate    		 Check CPU, memory, disk and network for utilisation, saturation and errors, then profile the busiest process. Name tools in order: uptime, top or htop, vmstat, iostat, then perf and a flame graph.
    What is the difference between RISC and CISC?
    Computer architecture · Concept · Current · Beginner    		 RISC uses simple, fixed-length instructions; CISC has complex, variable-length ones. Modern x86 decodes into simpler internal micro-operations. Mention Arm and RISC-V as RISC, x86-64 as CISC, and that the line has blurred in practice.
    What is a deadlock and how do you prevent it?
    Operating systems and concurrency · Concept · Current · Intermediate    		 Threads wait forever for locks held by each other; prevent it by always acquiring locks in a fixed order or using timeouts. Name the four Coffman conditions and say which one your fix breaks.
    Why can memory be the bottleneck, not the CPU?
    Memory hierarchy; roofline model · Concept · Current · Advanced    		 Cores compute far faster than DRAM can supply data, so low-reuse code waits on memory. Mention the roofline model, arithmetic intensity and fixes such as tiling and better data layout.
    How does a computer boot?
    Firmware and operating systems · Concept · Current · Beginner    		 Firmware (UEFI) initialises hardware, finds a boot loader, which loads the kernel; the kernel then starts the first user process. Mention Secure Boot checking signatures, and systemd as PID 1 on most Linux systems.
    TLB miss vs page fault?
    Memory management · Concept · Current · Intermediate    		 TLB miss: the translation isn't cached, so hardware walks the page table. Page fault: the page isn't mapped or present, so the OS steps in. Add scale: a TLB miss costs tens to hundreds of cycles, while a major page fault that reads from disk can cost milliseconds.
    How would you debug a slow GPU training job?
    ML infrastructure · Concept · Current · Advanced    		 Check GPU utilisation and memory, then profile to see whether the GPU waits on data loading, CPU work, communication or slow kernels. Name nvidia-smi, Nsight Systems and PyTorch Profiler; fixes include more loader workers, mixed precision and overlapping communication with compute.
